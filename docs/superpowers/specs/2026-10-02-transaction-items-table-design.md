# 品目テーブルへの移行設計

## 目的と範囲

支出の品目を `transactions.items_json` から独立した SQLite テーブルへ移す。利用者に見える画面、API の入出力、取引の表示順、品目の表示順は維持する。品目単位の検索・集計・編集は今回追加しない。既存 DB の取引と品目を失わず、新しい保存形式へ一度だけ移行する。

対象は `backend/store.py` のスキーマ、移行、保存、取得、削除処理と、そのテストである。フロントエンドと HTTP エンドポイントの変更は必要ない。

## スキーマ

`meta` は現状を維持する。`transactions` は `items_json` 列を除き、ほかの列を維持する。品目は次のテーブルに保存する。

```sql
CREATE TABLE transaction_items (
    transaction_id TEXT NOT NULL REFERENCES transactions(id) ON DELETE CASCADE,
    position INTEGER NOT NULL CHECK (position >= 0),
    name TEXT NOT NULL,
    amount INTEGER NOT NULL CHECK (amount > 0),
    PRIMARY KEY (transaction_id, position)
);
```

`position` は配列内の 0 から始まる順序である。同じ名前・金額の品目が複数あっても別行として保存できる。個別品目の編集機能がないため、独立した品目 ID は設けない。品目なしの取引は関連行を持たない。SQLite の外部キーを各接続で有効にし、取引削除時に関連品目を削除する。

## 既存 DB の移行

起動時に `transactions` の列を調べ、`items_json` がある場合だけ移行する。既存の各行から JSON を読み、配列の順序を `position` に写す。JSON が読めない、または品目の構造・金額が既存の取引と整合しない場合は移行を失敗させる。正常な既存データを移した後、`items_json` を除いた `transactions` を作り直して品目テーブルを作る。全操作を一つの SQLite トランザクションで行い、失敗時は元のスキーマとデータを残す。成功後の再起動では移行を繰り返さない。

新規 DB には最初から新スキーマを作る。`meta.initialized` による初期取り込みの判定は維持し、移行済みの DB を再初期化しない。

## 保存・取得・削除

取引の初期取り込みと新規作成では、親の取引行と品目行を同じトランザクションで保存する。既存の `normalize_transaction` による入力検証を使い、品目の合計が取引金額に一致する規則も維持する。保存に失敗した場合は親子とも取り消す。

一覧取得では取引を従来どおり `date DESC, id DESC` で読み、関連品目を `position` 順に組み立てる。単一取得も同じ形へ組み立てる。支出の API レコードには従来どおり `items: [{name, amount}, ...]` を含め、収入のレコードには品目を含めない。作成レスポンスも同じ形式を維持する。

通常の取引削除とサンプル取引の一括削除では、外部キーの `ON DELETE CASCADE` により関連品目を削除する。削除件数は引き続き取引の件数とする。

## 確認条件

- 新規 DB で品目あり・なしの支出と収入を保存、再起動後に取得できる。品目の重複と順序を保持する。
- 旧スキーマの DB を開くと、取引、品目、初期化状態を保持したまま移行する。再起動しても重複品目は生じない。
- 不正な旧 JSON による移行失敗後、旧スキーマと元データが残る。
- 取引削除とサンプル削除で孤立した品目が残らない。保存失敗時にも親子の片方だけが残らない。
- 既存の API テストを通し、品目を含むレスポンス形式とエラー形式を維持する。
