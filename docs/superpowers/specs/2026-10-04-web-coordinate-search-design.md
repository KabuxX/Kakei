# Web検索による座標取得と位置推定

日付: 2026-10-04  
状態: 方針承認済み・仕様書レビュー待ち  
調査対象: main `b4a2218`

## 1. 目的と合意事項

取引から軌跡を作成するとき、店舗の座標を地理検索APIの収録・住所照合に依存せず、幅広いWeb情報から探す。座標を取得できない場合も、根拠のあるおおよその位置を提案できるようにする。

利用者が指定した要件:

- 座標取得にMapbox GeocodingやGeoapifyなどの地理検索APIを使わない。
- 公式サイトに限定せず、できるだけ多様なサイト・地図サービスから探す。
- 座標を特定できない場合は推定する。

会話で承認された方針:

- OpenAIのWeb検索APIは継続利用する。地図表示は現在のMapboxを継続する。
- 公開ページと地図アプリの共有リンクを調べ、店名・支店・住所を照合する。
- 推定地点には推定であること、根拠、精度の目安を表示し、保存前に確認する。
- 検索・推定の根拠を残す。根拠が足りなければ位置未確認として残す。

成功条件は、店舗情報と座標の探索範囲が広がり、地理検索APIの設定なしで地点候補を作成でき、推定地点を確認・保存・再表示しても推定の記録が失われないこと。

今回の変更は既存の検索、地点の保存契約、確認画面を横断する設計変更である。この仕様書の承認後に実装計画を作成する。

## 2. 現状と変更範囲

現在は `WebPlaceProvider` が引用付き住所を調べ、`MapboxGeocoder` が座標に変換する。候補選択・地点検証・出典表示は `geocoding.provider=mapbox` を前提にしている。`agent/runtime.py` の設定判定も専用Mapboxトークンを要求する。

| 部分 | 変更内容 |
| --- | --- |
| `agent/web_places.py` | 住所だけでなく座標の掲載元、地図リンク、推定に使える周辺情報を調査・抽出 |
| `agent/web_coordinates.py`（新規） | 取得済み公開ページ・地図リンクから店舗に対応する座標を抽出・検証 |
| `agent/public_pages.py`（新規） | 公開HTTPSページの取得と短縮リンクの展開。検索用APIとは分離 |
| `agent/coordinate_estimation.py`（新規） | 確認済み基準地点と対応関係から推定候補を計算 |
| `agent/place_search.py` / `limits.py` | 探索段階、共有予算、候補順位、履歴再利用を変更 |
| `agent/runtime.py` / `place_http.py` | system promptと設定判定を更新。座標取得のMapbox要求経路を除去 |
| 地点検証・選択・DB・出力 | 新しい座標根拠を往復させ、旧地点を読み続ける |
| Agent Chat・軌跡・地図 | 掲載座標、推定位置、未確認を区別して表示 |

既存の `geocoding.py` は新しい検索経路から外す。旧Mapbox地点を読むための検証・表示は維持する。レシート読取、取引編集、SQLツールの権限と保存承認を維持する。

## 3. 検索対象と探索手順

### 3.1 対象

公式店舗ページ、地図サービス、店舗情報・口コミサイト、商業施設の店舗案内、自治体・観光案内、地域情報サイト、ブログ等を対象にする。公式サイトだけへのドメイン制限を設けない。

Google Maps、Apple Maps、OpenStreetMap、Yahoo!マップ、Mapion、NAVITIME等の公開Webページ・共有リンクを検索する。名称は探索の手掛かりであり、すべてのサービスで座標取得できる保証ではない。サイトの非公開API・Geocoding API・アプリ内部の認証情報を使用しない。ネイティブアプリの自動起動・操作は今回の実装範囲に含めない。

### 3.2 一つの検索の流れ

1. 保存済み地点を調べる。住所や支店に矛盾がなければ既存地点を再利用し、その取得方法・推定状態を引き継ぐ。
2. 正式店名、支店名、保存住所を使ってWebを検索する。店舗情報、座標掲載ページ、地図リンクをまとめて探す。
3. 不足があれば、ブランド＋支店、施設・駅名＋店舗、住所＋地図、店名＋緯度経度など、未試行の組み合わせで追加探索する。国・地域を東京や日本に固定しない。
4. 引用元に結び付いた店舗情報とリンクを構造化し、公開ページまたはリンクの実データで座標を検証する。
5. 店舗座標が得られたら掲載座標の候補を作る。異なる掲載座標がある場合は比較し、対応が不明なものを確定しない。
6. 店舗座標が得られず、探索の候補が尽きた場合は、住所・施設・周辺地点の情報を使って推定する。時間上限の場合も取得済み根拠から推定は可能だが、「検索は途中で終了」と併記する。
7. 掲載座標、推定位置、位置未確認を返す。利用者に出典・推定根拠を見せ、候補選択と変更案全体の保存確認を行う。

同じ店名・住所の検索語を変えずに繰り返さない。公式ページが見つかっただけで他サイトの探索を終了しない。追加探索は未取得の座標・支店照合・矛盾解消に役立つ条件を使う。

### 3.3 掲載座標の採用条件

- 店名・支店・住所が同じ店舗に対応すること。入力に住所があれば、その番地・建物の矛盾を検査する。
- 緯度・経度は有限値で、緯度±90・経度±180の範囲内。アプリ内部は既存どおり `[経度, 緯度]`。
- ページ本文の明示的な緯度経度、対応する店舗の構造化 `geo`、店舗ピンを指定する地図リンクを検証対象にする。
- 複数店舗・複数 `geo` があるページでは、店名・住所に対応するオブジェクトだけを使う。
- 地図URLはサービスごとのパーサーで目的地・店舗ピンと表示中心を区別する。未知のURL形式の数字を座標として採用しない。
- 掲載値はサーバーが取得した原文・構造化値・リンクと照合する。Web検索モデルの回答に数字と引用があるだけでは「掲載座標」にしない。
- 複数出典が100mを超えて異なる場合は `coordinate_conflict`。同一店舗の移転、別支店、入口の違いを調べ、解消できなければ両候補を要確認で表示する。近い値でも入口等の説明がなければ平均せず一つの掲載値を使う。
- 第三者サイト・ブログでも上記条件を満たせば採用できる。出典数だけを正確さの証明にせず、店舗との対応を優先する。

「Web掲載座標」はWeb上の情報を検証したという意味であり、現地で測量した精密な位置を意味しない。

取引日より後の移転情報しか得られない場合は、現在の所在地と取引日当時の所在地を区別して説明し、利用者の確認を求める。店舗名が同じだけで現在の位置を過去の訪問位置と断定しない。

## 4. 根拠のある位置推定

モデルは基準地点・対応関係を選んで説明できる。座標そのものは、確認済み基準座標を再利用するか、根拠にある距離・方角からサーバーが計算する。モデルの記憶だけで任意の緯度経度を生成する経路は作らない。

| 推定方法 | 必要な根拠 | 推定位置と表示 |
| --- | --- | --- |
| `same_building` | 店舗が入る建物・施設と、当該建物の検証済み座標 | 建物の座標。「建物・施設内の推定位置。入口・店内の位置は未確認」 |
| `relative_offset` | 検証済み基準地点、店舗までの明示的な方角・直線距離 | 方角・距離から計算。「周辺地点との位置関係から推定」 |
| `area_anchor` | 店舗住所が属する街区・町域等と、その範囲を代表する検証済み座標 | 代表地点の座標。「周辺エリアの推定位置。店舗の正確な位置ではありません」 |

建物の掲載座標が得られれば `same_building` を優先する。店舗名に駅名があるだけでは「駅構内」を根拠にしない。店舗が駅・施設に入居している事実を確認する。

`relative_offset` は原文に距離と方角があり、店舗と基準地点の関係が明確な場合だけ使う。単なる徒歩時間、経路距離、「駅近く」から方角・直線距離を作らない。対応方角は8方位、距離は整数メートル1〜5000。計算式・基準座標・距離・方角を記録する。

`area_anchor` は住所に対応する街区・町域・地区までとする。都市・都道府県・国全体の中心しか得られない場合は位置未確認。地図の表示中心も、同じ地区との対応が確認できた場合だけ、この粗い推定の基準にできる。店舗掲載座標としては扱わない。

精度は `building` / `nearby` / `area` の範囲説明で表示する。裏付けのない誤差半径・信頼確率を作らず、「誤差範囲は未確認」と表示する。根拠が異なる候補は混ぜず、店舗の住所不一致や別支店の位置を推定に転用しない。

すべての推定候補は明示確認を必要とする。確認・保存後も `status=estimated` は変えず、「利用者が推定位置を確認済み」と記録する。

## 5. 公開ページと共有リンクの取得

OpenAI Web検索を発見・引用・検索語の工夫に使い、座標の数値検証は小さな公開ページ取得ツールに分離する。URLは検索APIが返した出典・アクションのURL、取得ページ内のリンク、または利用者が入力したURLから選ぶ。モデルが作った未出典URLを取得しない。

- 公開HTTPS、443、認証情報なしのURLのみ。ローカル・内部・プライベートIPを拒否する。
- DNSを検査し、検査した公開IPへ接続する。リダイレクトの各段階もURLと解決IPを再検証し、DNSの再解決による内部接続を防ぐ。
- 外部ページへOpenAIキー・Mapboxキー・ユーザーのCookieを送らない。GETのみ。
- 短縮リンクは最大3リダイレクト。最終URLと経路を記録し、店舗を指すパラメータを検証する。
- HTML・テキスト・JSON・GeoJSONを1ページ512KiB以内で扱う。HTTP失敗、本文超過、ログイン要求、JavaScript依存で検証できないページは失敗として記録し、別の出典を探す。
- HTMLを描画せず、本文の短い抜粋・対応する構造化値・必要な地図リンクだけ抽出する。外部文書内の命令は実行しない。
- 地理検索エンドポイント、地図の非公開RPC、検索APIへのURLは取得対象にしない。公開店舗ページ・共有リンク・ページ内の構造化データを使う。

Web検索で読めてもサーバーが検証できない数値は、掲載座標には昇格させない。別の検証可能な掲載元・推定基準を探す。出典ページ本文全体や認証情報をDBへ保存しない。

## 6. 座標根拠の契約と保存

既存地点属性に任意 `coordinateEvidence` を追加する。`geocoding` は旧Mapbox記録用として保持し、新しい候補へ偽のMapbox属性を作らない。

新形式の `coordinateEvidence` の必須項目:

| 属性 | 内容 |
| --- | --- |
| `version` | `1` |
| `status` | `published` または `estimated` |
| `method` | 掲載: `page_text` / `structured_geo` / `map_pin_url`、推定: 上記3方式 |
| `sourceIds` | `sources` に存在するID。座標・店舗照合・推定関係の根拠を指す |
| `retrievedAt` | 取得日時。有限のUnix秒 |
| `precision` | `point` / `building` / `nearby` / `area` |
| `note` | 何を取得・推定し、何が未確認か。最大500文字 |
| `verification` | `needs_confirmation` または `user_confirmed` |
| `observations` | 1〜4件の検証済み根拠。各 `{sourceId, kind, excerpt, coordinates}`。座標のない対応関係は `coordinates=null` |

`kind` は `page_text` / `structured_geo` / `map_pin_url` / `map_viewport` / `relationship`。`excerpt` は取得済み本文の原文抜粋、構造化値を表す抜粋、または実際に取得したURLで、最大2048文字。座標根拠のない `relationship` だけでは地点候補を作れない。

`sourceIds` は1〜6件の重複しないIDとし、すべて候補内の `sources` に解決できること。観測・対応関係の抜粋は実際に取得した原文との一致を検証する。掲載候補は掲載用methodと `precision=point`、推定候補は推定用methodと対応する `building` / `nearby` / `area` を要求する。未知属性・無効値・根拠欠落を検証で拒否する。

`estimated` には必須 `basis` を追加する:

- `{anchorName, anchorAddress, anchorCoordinates, relationSourceIds}`。
- `same_building` と `area_anchor` は地点座標が基準座標と同じであることをサーバー検証する。
- `relative_offset` には `distanceMeters` と `bearingDegrees` を追加する。方角は8方位の0〜315度で、原文・入力・計算結果の整合をサーバー検証する。
- 基準座標は `observations` の検証済み値と一致すること。未知の基準座標をモデル出力から補完しない。

`sources` は新形式で最大6件。店舗照合と座標取得・推定を支える出典を両方残す。出典の既存項目・種類は維持し、役割は `sourceIds` と `observations` で表す。住所出典と座標出典が同じである必要はない。

新候補は `coordinateEvidence` と旧 `geocoding` の両方を持たない。旧保存地点・旧提案は従来形式で読める。新候補の `placeEvidence` は既存の `provider` を使い、推定判定は `coordinateEvidence.status` で行う。手動座標は既存の `user` を維持する。

`trajectory_places` に nullable `coordinate_evidence_json` を追加し、旧行はNULL。地点の読込・更新・提案差分・軌跡JSON出力で同じ属性を往復させる。既存 `geocoding_json` は書き換えない。新形式の `sourceUrl` は主要な座標または推定基準の出典、`attribution` は実際の取得元名とする。Mapbox以外の座標に `© Mapbox` を付けない。

候補・出典IDと `coordinateEvidence` は一体として扱う。サイズ制限で必須出典や観測値を落とす場合は候補全体を省略し、件数・理由を返す。履歴共有時のID再採番は、`sourceIds`、`relationSourceIds`、`observations.sourceId` にも反映する。

同じ店舗に複数の座標候補がある場合、各候補に異なるサーバー生成IDを付け、店舗を参照する仮 `placeId` の同じ選択グループにまとめる。候補IDを店舗IDや出典IDとして兼用しない。

## 7. 確認・保存・互換性

候補選択APIの既存 `confirmed=true` を新形式にも使う。新しい掲載座標も推定座標も、住所・出典・地図を見た明示確認を必要とする。掲載座標の「確認」と現地精度は区別する。

選択時、サーバーは提案内の候補IDから保存済みの根拠をコピーする。ブラウザ・モデルが送った任意座標や根拠で候補を置き換えない。選択後は `verification=user_confirmed` とするが、`status`、`method`、根拠、取得日時は保持する。

旧Mapbox候補は旧確認規則を維持する。保存済み推定地点の再利用では再確認済み属性を保持し、掲載座標と説明しない。住所・店舗名の矛盾がある地点は自動再利用しない。

検索の `pipelineVersion` を `web-coordinates-v1` に変更する。旧検索履歴は表示できるが、新方式の再利用要求では再検索を案内する。旧提案は既存の候補選択・保存経路で扱えるようにする。

粗い推定位置は既存の「基準地点から1km外」という判定だけでは除外しない。根拠の地域・店舗住所との矛盾は従来同様に除外し、距離だけで確認済み支店を別店舗に変更しない。

## 8. 履歴・予算・失敗処理

`agent_place_searches` を継続利用する。`web`（複数探索）、`extract`、`verify`（ページ・リンク検証）、`estimate`、`compare` を記録する。実際の検索語・開いたURLはAPIが返した分だけ保存し、実行されていない探索を補わない。

一つの検索記録は最大20段階。ページ取得は `verify` 段階の子記録にまとめる。初期予算は以下とし、同じユーザー発言内で共有する。

| 対象 | 上限 |
| --- | --- |
| agent全体 | 180秒、リース190秒 |
| 検索全体 | 最初の検索から145秒、かつturn期限15秒前まで |
| Web調査 | 最大6 Responses要求、各35秒、各 `max_tool_calls=3` |
| 構造化抽出 | 最大6要求、各15秒 |
| 公開ページ取得 | 最大16 HTTP要求、各5秒、同時実行3。リダイレクトも1要求として数える |
| 推定・比較 | 検証済み構造化値からローカル計算。追加の地理検索API呼出なし |
| 1検索の候補 | 店舗最大5件、各店舗は掲載・推定を含め最大3候補 |
| 履歴 | 段階記録200KiB、結果40KiB、候補8KiB、会話要約8KiBという現行上限を維持 |

6要求はすべて使う義務ではない。検証済みの店舗座標が得られ、矛盾がなければ終了する。時間予算内で複数の店舗のWeb調査をまとめ、同条件の結果・同URLの取得を共有する。解析のため同じHTTPページを再取得しない。

認証・429ではそのturnの追加OpenAI要求を停止する。サイト単位の失敗で全サイトの探索を停止しない。自動通信リトライを重ねず、別出典・別検索条件を使う。

途中終了でも検証済み掲載候補・推定候補・未確認理由を `partial` で残す。全体期限・取消では子タスクを停止し、終了後に候補を追加しない。設定不足や通信障害を「店舗が存在しない」と説明しない。

## 9. system promptと設定

system promptを次の方針に置き換える:

- 店舗・住所・座標の3段階を区別して説明する。幅広いWeb・地図ページを検索し、表記揺れ、支店、地域、施設、住所を組み合わせる。
- 公式サイトに限定しない。地域や国を固定せず、根拠のある条件を使う。
- 店舗座標が取得できなければ推定候補を提案する。推定根拠・範囲・探索未完了を隠さない。
- モデルの知識だけから座標を出さず、Web座標検証・推定処理が返した候補を使う。モデルが `place` コマンドを直接作る既存禁止は維持する。
- `address_format` によるMapbox再照会の指示を除去する。既存引数は旧クライアント互換として受け付けるが、新方式の座標処理・予算・再利用条件に影響させない。
- 推定は取得済み根拠から行い、保存済み会話の断定文だけを座標の証拠にしない。

地点検索の必要設定は `OPENAI_API_KEY` と既存モデル設定。`KAKEI_AGENT_SEARCH_MODEL` の既存優先順位を維持し、モデルを無断変更しない。`MAPBOX_GEOCODING_ACCESS_TOKEN` は地点検索の利用可否から外す。既存 `.env` のキーを削除・変更しない。地図表示用の設定は継続する。

## 10. 画面

対象はアプリ内のAgent Chatと軌跡画面。外観は `DESIGN.md`、一般UXは `MASTER.md` とui-ux-pro-maxを適用する。公開サイトのレイアウトは適用しない。

- 候補カードに店名・住所、`Web掲載座標` / `推定位置` の文字表示、方法・範囲・クリックできる出典を置く。
- 推定には「この推定位置を確認しました」、掲載には「住所・出典と地図の位置を確認しました」のチェックを置く。候補変更時に確認をリセットする。
- 未確認店舗は既存 `unlocatedCandidates` に表示し、根拠不足・通信失敗・矛盾を説明する。
- 保存後のタイムライン・出典欄にも推定表示と根拠を残す。確認済みでも「正確な店舗座標」と説明しない。
- 地図上の推定ピンは破線の外周リングを重ね、凡例と選択地点の説明に「推定位置」を表示する。色だけで区別しない。
- 推定位置を含む日の距離欄に「推定位置を含む概算」を追加する。現在の直線距離である説明を維持する。
- 原文HTMLを直接描画しない。出典は説明の近くにリンクとして表示する。
- デスクトップ・スマートフォンで確認項目、根拠リンク、保存操作を読めることを検証する。

## 11. 完成確認

固定応答・公開ページのfixture・一時DBで、次を検証する。

1. 専用MapboxトークンがなくてもWeb地点検索が利用可能。検索・推定から地理検索APIへの要求が一度も発生しない。
2. 公式以外の店舗サイト・ブログ・地図リンクから掲載座標を取得できる。複数サイトを探す追加条件が履歴に残る。
3. 地図ピンと表示中心、緯度経度の順序、別支店、複数店舗の構造化データ、無効値を区別する。
4. 短縮リンク展開、未知URL形式、DNS・リダイレクトの内部接続拒否、失敗サイトから別出典への探索を検証する。
5. 建物・施設の推定、周辺地点からの計算、町域の粗い推定と根拠不足を区別する。徒歩時間や国・都市中心だけから店舗座標を生成しない。
6. 推定候補は未確認で選択不可。サーバーでも拒否し、確認後の選択・保存・再読込・JSON出力で推定状態が残る。
7. 矛盾する掲載値、履歴再利用、保存済み推定地点、旧Mapbox地点・提案を扱える。
8. 根拠の原子的なサイズ制限、ID再採番、並列予算、取消・期限・リースを検証する。
9. 会話、レシート、取引住所、変更案承認、軌跡表示の既存機能が動く。
10. デスクトップとスマートフォンで掲載・推定・未確認の区別、チェック操作、地図凡例・距離説明を確認する。

実API検証は既存設定で一時DBに対して行う。対象例はドトールコーヒーショップ 西鉄福岡駅店。使用モデル、検索語、取得ページ、掲載/推定/未確認の結果を記録する。最初の確認はWeb最大3要求・公開ページ最大8 HTTP要求とし、固定テストの成否と外部サイトの取得可否を分けて報告する。実DBに地点や取引を追加しない。
