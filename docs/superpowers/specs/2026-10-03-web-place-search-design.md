# Agent の店舗検索を Web 検索と Mapbox に移行する

作成日: 2026-10-03
状態: 2026-10-03 利用者による本文承認済み。実装計画のレビューへ進む。

## 1. 目的と合意事項

Kakei で取引から軌跡を作る際、店舗の公式ページなどを検索して支店と住所を特定し、その住所から地図用の座標を取得する。Geoapify への新しい通信と設定依存を廃止する。

利用者は OpenAI Web 検索と別サービスによる住所の座標変換を選択し、Mapbox Geocoding API の永久保存モードを使う構成を承認した。店舗検索履歴、候補選択、保存前の確認を引き継ぐ。LangChain の単一 agent、FastAPI、ローカル SQLite、現在の Mapbox 地図表示を継続する。

成功とは、対象支店の根拠を示して住所を照合し、利用者が候補を確認して保存できること。Web にない店舗や、座標変換できない住所を必ず解決することは保証しない。今回の回帰対象は「ドトールコーヒーショップ 西鉄福岡駅店」。福岡や東京に固定した処理は設けない。

以下の期限・件数・画面表示は今回の設計案であり、本文の承認対象とする。まだ製品コードや環境設定は変更していない。

## 2. 構成と責務

| 部分 | 責務 |
| --- | --- |
| `agent/web_places.py`（新規） | OpenAI Responses API の Web 検索、引用付き調査結果、構造化抽出 |
| `agent/geocoding.py`（新規） | Mapbox Geocoding v6、住所照合、座標精度の正規化 |
| `agent/place_search.py` | 保存済み地点の照合、Web→住所→座標の実行、共有予算、部分結果 |
| `agent/place_matching.py` | 利用者の地域根拠、支店一致、地域矛盾、重複排除 |
| `agent/runtime.py` | 既存検索・履歴ツールを維持し、新サービスを接続 |
| `db/agent_search_store.py` | 各段階の結果・根拠・失敗の保存と会話単位の参照 |
| 地点選択・軌跡の検証と保存 | 新しい出典情報を保持し、従来データとの互換性を維持 |
| 候補カード・軌跡の出典表示 | 店舗情報と座標の根拠を分け、確認可能にする |

Web 調査は権限を持たない専用の API 呼び出しとする。SQL・編集・承認ツールや家計全体へのアクセスを付与しない。汎用 Web ブラウザ、別の自律 agent、バックグラウンドジョブ基盤は追加しない。

## 3. 検索の流れ

1. `search_place` の既存入力と地域根拠を検証する。最新の地域指定と過去の条件が矛盾する場合は検索前に確認を求める。
2. 保存済み地点が名称・支店・地域と一致すれば提示する。検索ツールに任意の `refresh=false` を追加し、利用者が再検索を求めた場合は `true` で Web へ進む。`refresh=true` と `reuse_search_id` の同時指定は拒否する。
3. Web 検索に店舗名、支店名、根拠のある地域・駅名だけを送る。正式名称を優先し、不足時は主要名称と地域を使って探す。公式店舗ページを優先するが、公式ページがないことだけで除外せず、情報サイトなどは出典種別を明示する。
4. 店舗候補を最大5件に構造化する。各候補に名称、支店名、住所、国・地域、引用元、確認できない点を持たせる。同じ候補内で別支店の住所を混ぜない。
5. 根拠付き住所だけを Mapbox に送り、返された住所と国・都道府県・市区町村・番地を照合する。建物名や階の省略は住所本体を保存した上で許容する。番地の削除や不一致を自動的に許容しない。
6. 選択可能な候補を最大5件表示する。店舗情報はあるが位置を確定できないものは別の「位置未確認」一覧に表示し、通常の地点選択には使えない。
7. 候補選択と既存の変更案承認を経て保存する。AI は座標や地点保存コマンドを任意に生成できない。

店舗名や住所が複数に解釈できる場合は選択・補足を求める。検索失敗は店舗の不存在を意味しない。現在の店舗ページを、取引日の営業状態や当時の住所の証明として扱わない。移転・閉店・住所の食い違いが分かれば未確認理由に残す。

## 4. OpenAI Web 検索と根拠の扱い

既存の `OPENAI_API_KEY` を利用する。検索モデルは `KAKEI_AGENT_SEARCH_MODEL` を任意設定とし、未設定時は `KAKEI_AGENT_MODEL` を継承する。現在指定されている `gpt-6-luna` は公式資料で Responses API の Web 検索対応を確認済み。アカウントでの実利用可否は実装時の接続検証で確認する。別モデルへの無断切替は行わない。

検索呼び出しは `web_search`、検索必須の tool choice、`store=false`、SDK 自動再試行なしとする。引用 annotations と `web_search_call.action.sources` を受け取る。検索語・開いた URL は API が返した分だけ記録し、内部で行われた検索を推測で補わない。

引用付き調査文を取得した後、ツールを付けない別の構造化抽出呼び出しで候補を整える。抽出器にはサーバーが割り当てた引用IDを渡し、自由な URL や座標の生成を採用しない。名称・住所を支える短い根拠文と引用IDを必須とする。引用IDが元応答に存在しない、根拠文が調査文に存在しない、住所が欠落する場合は選択候補にしない。

引用の存在と文字列照合は事実の正しさの完全な証明ではない。店舗情報は利用者に出典付きで確認してもらう。単に検索された URL 一覧にあるだけのページを、その住所の引用元とみなさない。公式性の自己申告だけを「確認済み」の判定に使わない。

Web 文書の命令はデータとして扱う。検索対象へレシート画像、支払額、品目、決済番号、会話全文を送らない。独自の任意 URL 取得器は作らず、ページ閲覧は OpenAI の検索機能内に限定する。出典リンクは HTTPS、認証情報なし、ローカルホスト・プライベートIPの直指定なしで検証する。識別に必要なクエリ文字列は保持し、キーを含む API URL は出典として保存しない。

## 5. Mapbox による座標変換

`/search/geocode/v6/forward` をバックエンドから呼ぶ。専用環境変数 `MAPBOX_GEOCODING_ACCESS_TOKEN` を使用し、フロント用 `VITE_MAPBOX_ACCESS_TOKEN` と用途を分離する。`permanent=true`、`autocomplete=false`、`language=ja`、最大5件とする。日本の住所と確認できた場合に `country=jp` を付け、海外住所は根拠のある国コードを使う。国や地域が分からなければ確認を求める。

永久保存モードには有効なクレジットカード登録または企業契約が必要。設定済み表示は認証・課金可否の保証ではなく、接続エラーは区別して案内する。永久保存モードが使えない場合に一時モードへ切り替えて保存しない。

座標は Mapbox 応答のみから取得し、経度・緯度の範囲、有限数、住所との対応をサーバーで検証する。`feature_type`、`match_code`、座標の精度を記録する。

- `address` または `secondary_address` で、指定した国・地域・番地に矛盾がなく一意に対応するものを選択可能にする。補間による座標にはその旨を表示する。
- `block`、道路、市区町村の中心など、住所の点まで確定しない結果は「位置未確認」とする。日本の街区結果も店舗の正確な位置と扱わない。
- 明示された住所要素が unmatched/inferred の場合や、比較に必要な情報が不足する場合は確認対象とする。モデルの「一致する」という判断だけで許可しない。
- 同じ住所の建物内に複数店舗がある場合、共有する建物座標から支店同一性は推論しない。

座標が未確認でも店舗名・住所・出典を失わない。利用者は既存の手動座標入力を使える。手動座標はユーザー指定として保存し、Mapbox 由来に偽装しない。

## 6. 候補・出典・既存データとの互換性

既存の候補ID、仮地点ID、候補選択API、変更案 revision を維持する。候補には次の情報を追加する。

- `sources`: 最大3件の `{id,title,url,kind,retrievedAt}`。店舗情報の引用元。`kind` は `official`、`directory`、`other`、`unknown` とし、判別できないものを公式に昇格させない。
- `geocoding`: `{provider,providerId,queryAddress,matchedAddress,featureType,accuracy,matchCode,permanent,retrievedAt}`。`provider=mapbox`、`permanent=true`。認証情報は含めない。
- `matchReasons`: 支店未確認・住所未確認・補間座標などの理由。

従来の `sourceUrl` は店舗情報の主要引用元、`attribution` は座標プロバイダーの帰属表示として維持する。保存する地点に `sources` と `geocoding` を任意属性として追加し、検証・更新・DB読書き・エクスポートで往復できるようにする。旧形式の地点はそのまま読める。候補選択時にサーバー保存済みの属性だけをコピーする。

検索結果には `unlocatedCandidates` を追加し、名称・住所・出典・未確定理由を持たせる。ここにあるIDを地点選択APIへ送っても拒否する。候補は1件8 KiB、結果全体40 KiB以内とし、現在の1候補2 KiB制限を出典情報に合わせて更新する。超過時は副次的な出典を丸ごと省略し、それでも収まらない候補は全体を省略する。

名称・完全住所の正規化と座標を合わせて重複を判定する。検索元のIDが違っても同じ店舗なら出典を統合する。別支店、同じ建物の異なる店舗、番地違いは統合しない。主要名称だけの一致では統合しない。

旧 Geoapify の保存済み地点、履歴、未承認提案は削除・書換えしない。旧提案は従来の候補選択と承認が可能。旧履歴は参照できるが、新しい検索の `reuse_search_id` で旧 Geoapify 検索を再利用せず、新方式での検索を案内する。保存済み地点そのものの利用は継続できる。

## 7. 履歴、期限、呼び出し予算

`agent_place_searches` を継続利用し、新記録の結果に `pipelineVersion=web-mapbox-v1` を付ける。各検索を `web`、`extract`、`geocode` の3段階で記録する。geocode 段階は住所ごとの要求・結果・失敗を子記録に持ち、各完了時に更新する。取消・モデル失敗でも完了済みの根拠を残す。

同じ会話の履歴のみを参照する。処理トークン、遅延書き込み拒否、会話削除時の削除を維持する。再利用は同条件・同方式・同じ地域根拠の終了結果に限る。参照と再検索を区別し、検索時刻を表示する。候補名・住所・URL・IDは切り詰めず、上限超過は候補または出典単位で省略し、件数と理由を残す。

初期予算は以下とし、1回のユーザー発言内で共有する。

| 対象 | 上限 |
| --- | --- |
| agent全体 | 120秒。API外側とRunnerで同じ定数を参照 |
| 検索全体 | 最初の検索から85秒、かつturn期限の10秒前まで |
| Web調査 | 最大3リクエスト、各最大35秒、各 `max_tool_calls=2` |
| 構造化抽出 | 調査1回につき1回、turn内最大3回、各最大15秒 |
| Mapbox | turn内最大10住所、各最大5秒、同時実行最大2 |
| 1店舗検索 | Web調査1回、抽出1回、異なる住所最大5件 |
| 出力 | 検索・抽出は各最大6,000出力トークン。外部HTTP本文は各512 KiBまで |
| 保存 | 1検索合計256 KiB以内、履歴応答32 KiB、会話用要約8 KiB |

内蔵ツール呼び出し数は検索クエリ数・課金額と同義ではない。APIが返す実際の使用量・呼び出し情報を記録する。リクエスト開始時に予算を予約し、並列実行でも上限を越えない。同じturn内の同条件の検索・住所変換は共有する。自動通信リトライは行わない。

処理中リースの失効時間は130秒とし、現在の70秒判定を一括更新する。ブラウザの待機表示を維持し、期限に達したら再送を案内する。検索内の期限切れは取得済み候補を `partial` で返す。agent全体が期限切れなら既存の失敗応答とし、履歴には完了した段階を残す。

認証・権限・429は該当プロバイダーの追加要求をそのturnで止める。Mapbox失敗時もWebの店舗情報を残す。履歴保存上限で候補を省略した場合も、その候補を未保存のままモデルや選択画面へ渡さない。

## 8. 画面と設定

画面は既存アプリ内の Agent Chat と軌跡の出典欄を小さく拡張する。`DESIGN.md` の外観、該当画面の情報階層、既存のアクセシビリティ方針を維持する。

- 候補カードに店舗名、住所、店舗情報のクリック可能な引用、座標の帰属・精度を表示する。
- 位置未確認候補は選択可能候補と分け、理由と既存の座標入力への案内を表示する。
- Web由来の説明を表示する際、その根拠リンクを説明の近くに表示する。候補だけでなく、変更案がない検索応答にもサーバー検証済み引用を返して表示する。本文を直接HTMLとして描画しない。
- 保存後も軌跡から店舗の引用元と座標の帰属を確認できる。
- 地点検索の利用可否はOpenAIと専用Mapbox設定で判定する。設定不足でも取引の会話、保存済み地点、手動座標は利用できる。

変更案がない応答の引用も再読込で失わないよう、`agent_messages` に既定値 `{}` の `metadata_json` を追加し、assistantメッセージに検索IDと検証済み `sources` を保存する。既存の位置指定INSERTは列指定に変更する。送信応答と会話読込は同じ任意 `sources` 属性を返し、旧メッセージは空配列として扱う。本文内の引用IDは当該メッセージの保存済み出典に解決できるものだけリンク化する。

Geoapify の接続コード、実行時の設定参照、説明文を新方式へ置き換える。未使用の同期 `search_places` も削除し、外部APIの公開契約として残さない。履歴・旧地点を読む互換処理は残す。既存 `.env` のキーを勝手に削除・書換えせず、新しい設定名と必要条件をドキュメントに記載する。

## 9. 完成確認

一時DBと固定応答で、通常の検索→住所照合→候補選択→承認→軌跡表示を検証する。加えて以下を回帰テストに含める。

1. 正式店名検索の不足を地域付き検索で補う。西鉄福岡駅店を別支店や駅の中心座標で置換しない。
2. 根拠のないURL、住所の欠落、別支店の住所、最新地域との矛盾、Webの指示文を候補確定に使わない。
3. 日本と海外の住所、番地不一致、街区のみ、補間座標、同じ建物内の別店舗を区別する。
4. Mapbox要求が常に永久保存モード。資格情報・レート制限・通信失敗で一時モードやGeoapifyへ戻らない。
5. 並列予算・キャンセル・120秒期限・130秒リース・同条件共有・不正な候補ID・履歴再利用の矛盾を検証する。
6. 新しい出典属性の保存と読込、旧地点・旧履歴・旧提案、会話削除、取引とレシートの既存経路を検証する。
7. デスクトップとスマートフォンで引用リンク、未確認候補、選択・保存の状態を確認する。

実API検証は既存設定が利用可能な場合に、一時DB、Web調査最大3リクエスト、Mapbox最大5住所で行う。店舗の根拠と座標精度、使用モデル、実行時刻を記録する。外部サービスの店舗収録、アカウントの契約状態、任意のモデル応答は固定テストの成功と区別する。必要な設定がなければ不足を報告し、別モデルや一時ジオコーディングで代用しない。
