# レシート登録時の店舗住所特定

日付: 2026-10-08

状態: チャット上の設計は承認済み。本文のレビュー待ち。製品コードの実装は未着手。

## 目的と合意事項

Agentでレシートを読み取って取引を登録するとき、店舗住所を取引情報に補足する。印字住所がなければ店舗名・支店名からGoogle Placesで検索する。店舗を一意に特定できない場合は、利用者に店舗候補の選択または支店名・地域の補足を求め、住所が解決するまで登録へ進めない。

利用者は次の方針を承認した。

- レシートに店舗住所があれば、その住所を使用する。
- 住所がなければ既存のGoogle Places検索を利用し、一意に特定できた店舗を補足する。
- 複数候補または候補なしでは、店舗・地域を利用者に確認してから登録する。住所を空欄にしたまま続行する操作は設けない。
- 解決後は、金額・品目・店舗情報を既存の変更案で確認して保存する。
- レシートや利用者入力の住所は住所欄に保存する。Google検索で得た住所は取引に関連づけたPlace IDから表示時に取得する。

成功条件は、住所付きレシートでは再入力せず登録でき、住所なしのレシートでは適合する店舗の住所を表示でき、曖昧な検索結果が誤った支店として保存されないことである。住所をGoogle参照から表示する場合、検索結果の住所文字列を恒久的な`merchantAddress`へコピーしたとは扱わない。

## 対象と現在の構成

対象はアプリ内のAgent Chat、レシート確認、変更案、取引詳細である。ダッシュボードの情報階層やレイアウトは変更しない。

現在の`agent/receipt.py`は印字された店舗住所だけを`merchant_address`として抽出する。`agent/runtime.py`が読取結果と重複候補を返し、`ReceiptReview.jsx`の入力から`AgentStore.create_receipt_proposal`が変更案を作る。取引は変更案の承認時に保存する。

取引の`merchantAddress`には既に保存・編集の経路があるが、レシート登録時の住所検索はない。Google Placesクライアント、店舗照合、Place IDからの一時表示APIは既存実装を利用できる。現在のGoogle訪問先解決は軌跡向けであり、レシートの確認状態や取引との関連づけは持っていない。

本変更では責務を次のように分ける。

| 単位 | 責務 |
| --- | --- |
| レシート抽出 | 印字値を抽出する。住所検索や店舗の推測をしない |
| 店舗照合サービス | 店舗名・支店名・入力された地域・住所で候補を比較し、一意・要確認・検索失敗を区別する |
| レシート店舗確認の保存層 | 会話とレシートに属する入力、候補ID、選択、確認状態、版を保存する |
| 変更案と承認処理 | 確認済みの入力と取引内容を照合し、取引・原本・地点参照を原子的に保存する |
| 住所表示 | 本人由来の住所または保存済みPlace IDから取引の住所を表示する |
| 確認フォーム | 不足情報の入力、再検索、候補選択、状態説明を行う |

過去の取引だけから住所を再利用する方式は、新規店舗を解決できないため主方式にしない。Geolonia・Web検索への切り替えや、店舗別の特別な分岐は追加しない。

## 読み取りから保存まで

1. レシートを既存の画像・PDF抽出処理で読む。税・金額・重複候補の判定は維持する。
2. 店舗名と非空の印字店舗住所があれば、`receipt_address`として解決済みにする。本社住所、電話番号、読めない住所の断片を代用しない。抽出時点で店舗住所として読めなければnullのまま確認対象にする。
3. 印字住所がなく店舗名がある場合、サーバーが初回検索する。店舗名がなければ検索せず、店舗名と地域の入力を求める。検索結果の本文をLLMに渡さず、状態と参照IDだけを渡す。
4. 一意に照合できた候補は`google_unique`として解決済みにする。店舗名・住所・Google Mapsへのリンクを確認フォームに一時表示する。
5. 曖昧な場合は候補選択、候補なしや情報不足では支店名・市区町村などの補足を求める。入力済みの金額や品目を保持し、レシートを再添付させない。
6. 利用者は補足して再検索するか、実際の店舗住所を直接入力して確認できる。直接入力は`user_address`として扱い、店舗名と非空住所の確認によって解決する。Googleの表示住所を編集可能な住所欄へ自動転記しない。
7. 解決済みになったら、既存どおり新規取引または重複候補の編集先を選び、変更案を作る。未解決ならサーバーも変更案作成を拒否する。
8. 変更案には取引内容と店舗の解決方法を表示し、利用者が「確認して保存」で承認する。登録成功の説明は保存完了後に出す。

重複候補の既存取引に住所があり、入力店舗名が同一なら、その住所を確認して使用できる。既存のGoogle参照も同一店舗名に限って確認して再利用できる。保存先を変えた場合、別の取引から引き継いだ確認は無効にする。新しい検索や入力で確認した住所は、店舗入力が同じなら保存先を変えても使用できる。

## 検索と店舗同一性

検索は既存の`GooglePlacesClient.search_text`を使う。送信するのは店舗名、支店名、利用者またはレシートに由来する地域・住所だけであり、金額、品目、原本、会話全体は送信しない。支店や地域をモデルで生成しない。

入力の制限は店舗名・支店名・地域各200文字、住所500文字以内とする。照合用に全半角、空白、ハイフン、英字の大小文字、住所の丁目・番地表記を正規化する。正規化によって支店の識別語を消さない。

初回は記録の店舗名を検索し、補足がある場合は支店名・地域・住所を含める。完全な入力と表記正規化した入力を最大2種類試す。同一文字列は重複送信しない。1回の検索処理は合計20秒以内、外部検索最大2要求、各通信最大8秒とする。レシート読取と初回検索は既存の180秒ターン期限を共有し、残り時間が足りない場合は確認画面で再検索できる状態を返す。独立した再検索リクエストも20秒を超えない。

候補は最大10件とし、自動ページ送りはしない。Place IDで重複を除く。住所が空、店舗ではなく住所・行政区画だけの地点、明らかな支店・地域・住所の矛盾がある候補は選択対象から除く。座標はレシートの住所解決条件にしない。軌跡作成の座標必須条件は維持する。

自動解決は、具体的な店舗名・支店名が一致し、入力された所在地情報と矛盾せず、同程度に適合する候補が一つの場合だけ行う。チェーン名だけで地域も支店も不明なら、検索結果が1件でも自動確定しない。候補の先頭、近さ、検索順位だけを根拠にしない。

支店の同一性が不足するが入力と矛盾しない候補は、利用者の選択対象として表示できる。サーバーは今回の候補群に属するPlace IDであることを検証し、選択時にDetailsを取得して非空住所と矛盾の有無を確認する。取得に失敗した候補は選択を完了させず、再試行を案内する。

既存の`VisitResolver`から必要な照合関数を共有できるが、軌跡側の判定を緩めてレシートに合わせない。住所だけを必要とする判定はレシート側に置く。

## 確認状態とAPI

`receipt_location_resolutions`を追加し、一つの会話とレシートに対する現在の確認を管理する。主要な保存項目は、会話ID、レシートID、確認UUID、版、入力店舗名・支店名・地域・本人由来住所、入力指紋、状態、候補Place ID群、選択Place ID、解決方法、取得日時、期限、分類済み理由とする。期限は最終検索または本人確認から24時間で、別会話からの参照は拒否する。

| 状態 | 表示と次の操作 |
| --- | --- |
| `needs_input` | 店舗名・支店・地域など不足する情報を入力する |
| `searching` | 店舗を検索中と表示し、重複検索を抑止する |
| `needs_selection` | 候補の店舗名・住所を表示して選択を求める |
| `resolved` | 住所または地点参照が解決済み。変更案へ進める |
| `not_found` | 条件に合う店舗がない。補足して再検索または住所を入力する |
| `unavailable` | 設定・通信・制限・時間切れの理由を表示し、再試行または住所入力を案内する |

レシート確認結果には`locationResolution`として上記の参照情報を追加する。会話を開き直しても最新の確認状態を取得できる。完了した過去のターンのJSONだけを現在状態として使用しない。検索中は開始日時と処理期限も保存する。処理期限は開始から20秒またはターン期限の早い方とし、期限を過ぎた`searching`は`unavailable`へ回収して再検索できる状態にする。

新しいAPIは会話配下の`/api/agent/threads/{thread_id}/receipts/{receipt_id}/location`を基点にする。

- `GET`: 現在の確認状態を取得する。Googleの表示内容は既存の`/api/places/google/{place_id}`で一時取得する。
- `POST .../search`: 店舗名・支店名・地域・本人由来住所と期待版を受け取り、検索する。
- `POST .../selection`: 確認UUID、期待版、候補Place IDを受け取り、候補選択を確定する。
- `POST .../address`: 期待版、店舗名、利用者が入力して確認した住所を受け取り、本人入力による解決にする。

初回検索はrunnerから同じサービスを利用する。未作成状態での期待版は0とし、作成後は増加する版を要求する。外部通信中はDBトランザクションを保持しない。完了時に確認UUID・期待版・入力指紋を比較し、入力を変更した後に返ってきた古い検索結果で現在状態を上書きしない。同一版の並行検索は一つだけ受け付ける。

既存の`receipt-proposals`には確認UUIDと版を追加する。サーバーは現在の確認と取引draftの店舗名・本人由来住所・保存先依存性を照合し、解決方法とPlace IDをサーバー管理の変更案metadataへコピーする。クライアントが指定したPlace IDや`resolved=true`をそのまま信頼しない。

変更案metadataには`receiptLocation`として入力指紋、解決方法、Place IDまたは本人由来住所、期限を保持する。Googleの候補名・住所本文は含めない。承認済みの確認を変更案に固定した後は、確認フォームでの別検索だけで変更案を書き換えない。

## 取引保存と変更後の扱い

`transaction_merchant_places`を追加し、取引IDを主キー・外部キーとして、Google Place ID、解決方法、本人由来の照合入力、確認日時を保存する。取引削除時は関連行も削除する。軌跡イベントを作らずに取引と地点を関連づけられる形とし、レシート登録から軌跡を自動作成しない。

取引の読取APIは任意の`merchantPlace`として`provider=google`、`placeId`、解決方法を返す。Googleの表示住所は取引レコードの恒久的な一部にしない。既存の取引追加・編集APIは、任意のPlace IDを受け取って関連行を作成できない。

変更案承認では、版、期限、入力との結びつき、既存取引の競合を検証し、取引・品目・原本添付・地点関連・承認結果を一つのSQLiteトランザクションで保存する。本人由来住所を使う場合は`merchantAddress`に保存し、不要なGoogle関連を残さない。Google参照を使う場合は、そのGoogle住所を`merchantAddress`へ保存しない。既存取引の本人由来住所をGoogle参照に置き換える場合は、住所欄をnullへ変更する差分と地点参照の追加を変更案で明示する。新しいレシート変更案は本人由来住所とGoogle参照の一方を採用し、古い住所が新しいGoogle住所を隠す状態を作らない。

取引の元データ指紋には地点関連も含める。旧取引・旧変更案は地点関連なしを既定として扱い、null追加によって旧指紋を壊さない。同じ承認の再送は既存の保存結果を返し、二重登録しない。

レシート確認中に店舗名・支店・地域・住所が変わった場合は、以前の確認を無効にする。金額・品目・支払方法だけの変更では店舗確認を無効にしない。変更案の「内容を修正」で店舗名・住所を変えた場合も承認を拒否し、元のレシート確認で店舗を解決し直して同じpending変更案を新しい版へ更新する。新しい確認UUIDと版を渡す再確認操作を追加し、既存のpending変更案を返すだけの冪等処理と区別する。

保存済み取引を通常の編集画面やAPIで変更した場合、店舗名変更、住所の明示的変更、支出から収入への変更ではGoogle関連を解除する。金額・品目・日時など店舗を変えない編集では維持する。住所の明示的削除でも古いGoogle住所を再表示しない。既存の軌跡との整合性検証は維持し、共有地点や保存済み訪問を自動で書き換えない。

新しいレシート経路で住所解決を必須にし、既存の通常取引登録、レシート以外のAgent変更案、既に発行済みの旧レシート変更案には新しい必須条件を遡及適用しない。DB移行で既存の取引住所を埋めたり、実DBを自動検索したりしない。

## 画面と表示

レシート確認フォームに「店舗・住所」のまとまりを追加し、読み取り値、検索中、店舗確認待ち、確認済みを文章で区別する。地域の入力と候補選択は必要になったときに表示する。未解決時は「変更案を確認」を無効にし、その近くに不足情報と次の操作を示す。

候補は店舗名・住所・Google Mapsへのリンクを縦に表示し、キーボードでも選択できる。取得に失敗した候補は選択を無効にし、再試行を提供する。検索失敗を「店舗が存在しない」と表示しない。入力欄のエラーを欄に結びつけ、送信に失敗したらエラー要約へフォーカスする。検索状態はstatus領域で通知する。

取引詳細では本人由来の`merchantAddress`を優先する。住所欄が空で`merchantPlace`がある場合はGoogleのDetailsを取得して住所を表示する。取得に失敗しても取引と地点関連は保持し、「住所を取得できませんでした」と再読み込み操作を表示する。Google表示情報はフォーム初期値、会話本文、履歴JSON、変更案のbefore/afterへ転記しない。

Google由来の表示にはGoogle Mapsと必要な第三者帰属を添える。既存の`GooglePlaceResults`と一時表示APIを活用し、店舗選択・再試行に必要な操作を追加する。表示APIはno-storeを維持する。CSVの住所列には従来どおり本人由来の`merchantAddress`だけを出し、Google参照住所を自動取得して書き出さない。

見た目は`DESIGN.md`、一般UXは`design-system/household-budget-app/MASTER.md`、操作・アクセシビリティは`ui-ux-pro-max`に従う。公開サイトのheroや宣伝用レイアウトを適用しない。デスクトップと375px幅で候補名・住所・未解決理由・主操作を読めることを確認する。

## 情報の由来と保持

GoogleのPlace IDは保存できるが、Places APIの表示内容を恒久保存することは許容された例外に限定される。本変更は既存アプリと同様にPlace IDだけを恒久参照として扱い、名前・住所・帰属情報は画面表示時に取得する。[Google Placesのポリシー](https://developers.google.com/maps/documentation/places/web-service/policies)

候補ID、選択ID、判定コード、本人由来の入力、日時は保存する。Google取得の名前・住所・座標・生レスポンスは新しい確認テーブル、会話、変更案、ログへ保存しない。候補選択はGoogle住所を本人由来の住所に変換する操作ではない。レシート原本の保持は既存仕様を使う。

会話削除では未承認の確認行を削除する。承認後の取引地点関連は取引に属し、会話削除後も保持する。旧検索履歴や旧プロバイダー実装は変更しない。

## 完成条件と検証

テストは固定Google応答、スクリプト化したモデル、一時DBを使い、普段使いのDBには取引を追加しない。

1. 印字店舗住所を再入力せず保存でき、本社住所や読めない住所を店舗住所に代用しない。
2. 住所なし・具体的な支店名ありで、一意な候補を解決し、承認後に取引とPlace IDが保存される。
3. 同名の別支店が複数ある場合、候補選択または地域補足まで変更案作成と保存を拒否する。
4. チェーン名だけの場合は結果1件でも自動確定せず、利用者の店舗確認を要求する。
5. 候補なし、設定不足、通信失敗、時間切れ、Details失敗を区別し、再試行または本人入力で回復できる。
6. 別会話の確認ID、候補群にないPlace ID、改ざんした解決状態、古い版、期限切れの参照を拒否する。
7. 店舗情報変更後の遅い検索応答が新しい入力を上書きせず、再確認したpending変更案は版が更新される。
8. 保存先変更で既存取引由来の確認を流用せず、同一店舗の既存住所・地点参照は確認して使用できる。
9. 金額修正では確認を維持し、店舗・住所変更では以前の確認を無効にする。保存済み取引の編集・住所削除・取引削除で関連の維持または解除が正しい。
10. 保存途中の失敗は原子的にロールバックし、再承認で取引・原本・関連行が重複しない。地点関連の競合も検出する。
11. Googleの住所が一時表示でき、取得失敗時には取引を維持して再読み込みできる。Google取得内容が恒久保存やCSVへ混入しない。
12. 旧DB・旧変更案・通常取引編集・税計算・重複検出・iPhone画像入力・軌跡作成が成立する。
13. 実APIモードとmock/demoの双方で表示を確認する。オフラインdemoは既存の固定データを使い、新たなGoogle検索は行わない。
14. デスクトップと電話幅で、未解決の説明、地域入力、候補選択、変更案への復帰、保存後の住所表示を確認する。キーボード操作、読み上げ状態通知、二重送信抑止も検証する。

実APIによる追加確認を行う場合は検索と表示の読み取りだけとし、候補件数や特定店舗のGoogle収録を成功保証にしない。
