# Geolonia を優先する Agent の座標検索

作成日: 2026-10-04

状態: 2026-10-04 利用者による書面承認済み。

## 1. 目的と合意事項

Kakei の Agent が店舗の座標を探す際、Geolonia japanese-addresses-v2 を優先して利用する。住所表記の違いによる失敗には、意味を保った表記変換で繰り返し照合する。詳細な座標を得られない場合は、既存の Web 検索・出典検証へ進む。

利用者が選択した方針は次のとおり。

- 公式 `@geolonia/normalize-japanese-addresses` を Node.js の小さな補助プロセスで使用し、Python が検索全体を管理する。
- 町丁目の代表座標だけが得られた場合は補助情報として保持し、Web で詳細な位置を探す。Geolonia の粗い座標を保存候補にはしない。
- 住所の異なる表記を最大6種類試す。Geolonia に使う時間は検索1回につき合計30秒以内とする。
- 保存前の地図確認と変更案の承認を維持する。

成功とは、根拠のある住所を柔軟に照合し、住所と座標の双方が十分に詳細な候補を返せること、または理由を記録して Web へ切り替えられることである。Geolonia の住所座標だけで店舗の入口や訪問当時の所在地を確認済みとは扱わない。

## 2. 現状と変更する境界

現在の `PlaceSearchService` は、保存済み地点・明示的な検索履歴再利用を確認した後、Web の店舗探索、情報抽出、公開ページ検証、根拠に基づく位置推定を実行する。住所・地域の根拠は `EvidenceResolver`、座標の証拠は `coordinate_evidence.py`、検索の試行と結果は `AgentSearchStore` が管理している。

これらの責務を保ち、住所から位置を取得する Geolonia 接続を追加する。

| 部分 | 責務 |
| --- | --- |
| `backend/agent/place_search.py` | Geolonia 優先、Web への移行、店舗同一性確認、検索予算・履歴との統合 |
| 新規 Python の Geolonia 接続モジュール | 住所変種の生成、Node プロセス管理、応答検証、詳細度判定、証拠への変換 |
| 新規 Node 補助モジュールと専用 package/lock ファイル | 公式ライブラリの呼び出し、限定したデータ取得、取得証跡、取得データの再利用 |
| `backend/agent/runtime.py` | 接続の生成・終了と、検索順序・粒度を説明する Agent 指示 |
| `backend/services/coordinate_evidence.py` と関連保存処理 | 住所対応座標の新形式の検証、出典の付け替え、候補選択と保存 |
| `backend/db/agent_search_store.py` | 新しい試行情報の保存、履歴と候補の証拠を一体で保持 |
| `front/src/CoordinateEvidence.jsx` と出典・候補表示 | 住所対応座標、照合住所、粒度、Geolonia の出典表示 |

公開 `search_place` の既存必須引数を変えない。Geolonia の専用ツールや新しい検索画面は追加しない。汎用の地域検索、海外住所の正規化、データセットの全件取込・自前ホスティング、無関係な検索処理の再構成は対象外とする。

## 3. 検索の順序

1. 既存の根拠検証を行う。住所・地域の矛盾や店舗の曖昧さがある場合は、具体的な確認を求める。
2. 条件が一致する保存済み地点、または利用者が明示した有効な検索履歴の再利用は、従来どおり外部通信なしで返す。Geolonia 優先は新しい外部座標取得に適用する。`refresh` は保存済み地点による省略を避ける。
3. 根拠のある日本の住所がある場合は、Web による座標取得より先に Geolonia で照合する。店舗名だけを住所として送らない。国が日本語の店名だけから推測された場合や、明示された国が日本以外の場合は、Geolonia を省略する。
4. 住所が不明なら、Web で対象店舗と住所を調べる。名称・支店・地域の同一性が検証された住所を得た時点で、残っている Geolonia の試行枠・時間を使う。Web は住所発見に先行できるが、新しく得た住所の座標取得では Geolonia を先に試す。
5. Geolonia で住所と座標が番地・住居番号まで照合できれば、その店舗の住所対応座標を候補にする。依然として店舗同一性の条件を満たす必要がある。確かな候補が得られた時点で追加探索を打ち切れる。
6. 対応なし、粗い結果、照合不一致、利用不能、通信失敗、時間切れなら、理由と補助情報を保持して既存の Web 座標取得・検証へ進む。

Web が独立した根拠によって返す推定候補は、従来の精度・確認条件に従う。Geolonia の町丁目座標を、そのまま Web の店舗座標や建物座標に付け替えてはならない。

複数の住所が異なる店舗・支店を指す場合は、表記違いとして混ぜない。曖昧さを残したまま最初に照合した住所を採用しない。同一店舗の独立した座標証拠が複数ある場合は、既存の座標比較と差異の説明を継続する。

## 4. 柔軟な再試行

住所変種はサーバーが生成し、元住所と変換方法を保持する。次の順で、元と異なる文字列だけを試す。

1. 元の住所。
2. 郵便番号と独立した国名「日本」を分離した住所。
3. NFKC、空白、ハイフン類を整理した住所。
4. 丁目・番・号の表記とハイフン表記を対応させた住所。
5. 建物名・階・部屋番号を明確に分離できる場合の住所本体。
6. 根拠に含まれる都道府県など、省略されていた行政区分を補った住所。

各変換は必要な場合だけ生成し、前の整理を組み合わせられる。公式ライブラリ自体の正規化も利用する。住所本体を安全に分離できない場合は、曖昧な末尾を勝手に削らない。番地・枝番・住居番号を落とした変種は作らない。存在しない都道府県、市区町村、丁目を補わない。

最大6種類は検索1回の全住所を通した上限とし、Web で住所が見つかっても枠をリセットしない。同じ入力は検索中に再実行しない。照合成功で停止し、データ未収録・不一致なら次の有効な変種へ進む。通信障害で同じ表記を再送する処理と、住所表記の変更は別の試行種別として記録する。

一時的な通信障害には、公式ライブラリの再送機構を利用し、同じ取得対象・範囲に対して初回と最大2回の再送までに制限する。アプリ側で再送を重ねて回数を増やさない。再送を使い切った取得障害は住所変種を替えて再送せず、Web へ切り替える。全体期限に達したら待機・通信を含めて終了する。住所に一致しないという正常な結果を通信障害として再送しない。

## 5. 詳細度と候補の採用条件

公式正規化結果の `level` と `point.level` を別々に検証する。番地まで住所を認識していても座標が町丁目代表点の場合があるため、住所の認識だけでは採用しない。この区別は[公式ライブラリの説明](https://github.com/geolonia/normalize-japanese-addresses)に基づく。

Geolonia の保存可能な候補は、次の条件をすべて満たす。

- `level == 8` かつ `point.level == 8`。
- 緯度・経度が有限で有効な範囲にあり、ライブラリが実際に返した座標と一致する。
- 正規化した都道府県、市区町村、町丁目、番地・住居番号が根拠住所と一致する。建物・階など分離済みの部分は比較対象から分けるが、住所本体の数字の違いを許容しない。
- 店舗名・支店・地域が根拠と一致し、複数候補や別支店の未解決事項がない。

町丁目、自治体などの粗い座標は、照合結果・粒度・採用しなかった理由を検索履歴へ保存する。選択可能な `candidates` には入れず、位置未確認の店舗情報や検索の補助情報に関連付ける。Geolonia の成功だけで訪問日の営業場所を保証しない。既存の訪問日注意書きを維持する。

## 6. Node 接続・通信・時間制限

公式ライブラリを専用の小さな Node パッケージに置き、バージョンと依存を lock ファイルで固定する。Python はシェルを介さず補助プロセスを起動し、標準入力・出力の JSON でやり取りする。Python 側の入出力・件数・サイズ検証を通らない応答から候補を作らない。

Node は検索中の複数照合を扱い、ライブラリの取得キャッシュを同じ検索内で再利用する。同一発言の同一条件は既存の共有処理に接続し、別プロセスの重複実行を避ける。長期キャッシュや検索履歴を最新データとして自動利用する仕組みは追加しない。

Geolonia に費やす実行時間の合計は、プロセス起動・照合の枠待ち・通信の再送待機・住所変換を含めて30秒以内。住所発見前後で分かれて照合しても合算する。Geolonia を実行せず Web の住所探索を待っている時間はこの30秒には含めないが、共通の検索期限には含める。既存の検索期限145秒・発言期限180秒・最終応答の予約時間15秒を延長しない。各開始時には共通の残り検索時間から Web 用に少なくとも35秒を残した範囲で Geolonia の期限を短くする。残り時間が足りない場合は新しい Geolonia 処理を開始しない。

期限、発言キャンセル、処理終了時に補助プロセスを終了・回収し、外側の処理後に通信を続けさせない。並行検索も既存の発言期限を共有し、プロセス数は発言内で最大2個に制限する。

データ取得先は公式の `japanese-addresses-v2.geoloniamaps.com` の HTTPS API に固定する。ユーザーやモデルから取得先URL、任意ファイルパス、コマンドを指定させない。ライブラリの Node 向け取得処理に制限と証跡収集を追加する。[公開された Node 実装](https://github.com/geolonia/normalize-japanese-addresses/blob/master/src/main-node.ts)の取得ハンドラーを利用できるという判断はソースからの推論であり、固定したバージョンで契約テストする。

Range 取得では応答ステータス・Content-Range と対象範囲を検証し、サーバーが範囲指定を無視して巨大ファイルを返しても全件を読み込まない。1応答8 MiB、検索1回の合計32 MiBを上限とし、超過は利用不能理由として Web へ移る。固定ホストの外へのリダイレクト、資格情報付きURL、非公開IPへの接続を許可しない。APIキーは必要ない。

Node 未導入、依存未導入、起動失敗、取得失敗、応答異常は、Geolonia の利用不能理由を保存して Web に進む。Geolonia の障害は OpenAI や公開ページ取得プロバイダーの停止状態へ伝播させない。Node がなくても既存アプリは起動できる。README に必要な Node バージョン・依存の導入方法と代替動作を書く。

## 7. 証拠と検索履歴

既存の Web 用 `coordinateEvidence.version == 1` は維持し、Geolonia 用に version 2 を追加する。新形式は `status: address_matched`、`method: geolonia_address`、`precision: address` とし、掲載された店舗ピンや近隣からの位置推定と区別する。

新形式は既存共通フィールドに加え、`addressMatch` に以下を保持する。

- プロバイダー名、公式ライブラリのバージョン。
- 元の住所、実際に送った住所、照合住所、適用した変換方法。
- 住所の `level` と座標の `pointLevel`。
- 都道府県・市区町村・町丁目・番地等の照合した構造化値。
- 取得元URL、取得日時、取得範囲、取得データのハッシュ、データ更新日時（取得できる場合）。

`observations` は `geolonia_address` の種別で、照合レコードの必要な抜粋・座標・出典IDを保存する。データ全体は保存しない。座標と照合住所を観測値に対して検証し、出典IDは候補の出典集合へ解決されなければならない。保存時にモデルやクライアントが照合結果を差し替えられない既存の候補検証を維持する。

出典は既存の形式を維持し、データセットを `kind: directory` として記録する。店舗・住所の裏付けとなる出典と、座標を取得した Geolonia の出典を両方保持する。最大6出典という制限内で、採用した証拠に必要な出典を欠落させない。取得範囲などの証跡は出典に参照を持つ `addressMatch` 内へ置く。

検索試行には、入力、変換方法、開始・終了時刻、照合結果、2種類の粒度、除外理由、障害種別、Web へ切り替えた理由を保存する。住所なしで省略した場合、Node がない場合も「照合して0件」と混同しない。履歴の既存サイズ制限を守り、採用候補と証拠を一体で保持する。

検索の `pipelineVersion` を更新する。旧履歴・旧提案・旧保存地点は読めるようにし、既存 v1 の選択・承認も壊さない。旧方式の履歴を新方式の検索結果として明示的に再利用する場合は、従来の版検査によって再検索を求める。JSON 列の追加情報で記録し、過去データの書き換えは行わない。

## 8. 利用者への表示と保存

アプリ内の候補・変更案・保存済み地点の根拠表示を拡張する。既存の地図と確認動線を使い、Geolonia 候補には「住所に対応する座標」と表示する。照合住所、番地・住居番号まで照合したこと、店舗の入口は未確認であることを示す。確認後は利用者の確認状態を表示するが、証拠の種類や粒度は変更しない。

Geolonia と japanese-addresses-v2 の名称、データセットへのリンク、CC BY 4.0 の帰属表示・ライセンスリンクを示す。データのライセンスは[公式データセット](https://github.com/geolonia/japanese-addresses-v2)に従う。加工して利用していることを明示し、店舗の公式情報と混同しない。

粗い結果は会話で「町丁目まで照合できたため、詳細な位置を Web で検索した」と説明できるが、保存ボタンの対象候補にはしない。検索の失敗と候補なし、部分成功を分け、Geolonia が失敗しても Web で有効な候補を得られた場合は、その結果と実行した範囲を伝える。

対象はアプリ内の地点確認画面であり、公開サイトやダッシュボードの配置は変更しない。UI 実装時には `DESIGN.md`、`design-system/household-budget-app/MASTER.md` と ui-ux-pro-max の指針を読み、既存の表面・文字・操作を保つ。

## 9. 完成条件と検証

固定した公式ライブラリ、固定応答、模擬 Web、隔離 SQLite を使って再現可能な検証を行う。実ユーザーデータへ保存する検証は行わない。

1. 根拠住所がある場合、Geolonia が Web 座標取得に先行し、詳細な一致で不要な Web 検索を省略できる。
2. 住所がない場合、Web で店舗住所を特定してから Geolonia を使い、店舗名だけを正規化しない。
3. 郵便番号・国名・全半角・丁目と番地・建物名の表記違いで、意味を保った変種だけを重複なく試す。別番地、別支店、根拠なしの地域補完を拒否する。
4. `level == 8` で `point.level == 3`、町丁目までの認識、座標なしは保存候補にならず Web へ進む。両方8の場合も住所・店舗照合を通す。
5. 通信障害の再送と住所変種の試行を区別し、6変種・30秒・共通発言期限・サイズ上限・並行数上限を守る。
6. Node/依存の不在、非正常終了、巨大応答、範囲不整合、時間切れ、キャンセルを扱い、残るプロセスや無期限通信がない。Geolonia の失敗後も Web が使える。
7. 検索履歴、再利用、出典IDの付け替え、候補選択、承認、保存後表示を通じて照合記録が維持される。偽造・欠落した v2 証拠を拒否し、既存 v1 を読む。
8. Desktop・phone 幅で、住所対応座標と Web 掲載・推定座標が区別され、出典、確認状態、地図確認、承認操作が読める。粗い座標が選択可能候補に混ざらない。

実接続は読み取りのみで詳細住所・粗い住所を確認する。収録状況が変わるため、特定店舗の成功や件数は保証せず、返された粒度と移行理由を確認する。既存の backend/frontend 回帰検証と production build を行う。
