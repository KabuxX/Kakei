# Google Places API (New)による軌跡の直接作成

日付: 2026-10-04

状態: 2026-10-04に本文のレビュー・承認済み。実装は未着手。

## 目的と合意事項

ユーザーが「2026年10月1日の取引記録によって、軌跡を作って」と指示すると、対象日の取引から訪問先を検索し、特定できた訪問を保存する。候補選択、住所・地図の確認、訪問順の確認、変更案の承認は要求しない。

ユーザーの指定は以下のとおり。

- 検索にはGoogle Places API (New)を利用する。
- Geolonia japanese-addresses-v2とWeb検索を現在の実行経路から外す。実行コードは削除せず保存する。
- サーバー用APIキーはルートの`.env`に設定済みの`GOOGLE_PLACES_API_KEY`を利用する。
- 特定できた訪問だけ保存する。除外した訪問は、対象の取引と理由を結果に表示する。
- 軌跡作成の指示が保存の許可となる。アプリ内で追加の確認を求めない。

この仕様での「特定」は、記録にある店舗名・支店名・住所とGoogleの候補が矛盾せず、同程度に適合する別候補が残らないことを意味する。検索結果の先頭であることだけを根拠に保存しない。

## 採用する構成

軌跡作成専用のサーバー処理を設ける。Agentは現在のユーザー発言から作成意図と対象日を読み取り、専用ツールを呼ぶ。検索条件の組み立て、候補判定、訪問IDの生成、保存内容と結果一覧の組み立てはサーバーで行う。

既存の変更案を生成して内部で自動承認する方式は採用しない。新しい作成経路は、候補グループ、変更案の版、24時間の承認期限、`user_confirmed`に依存しない。機械が解決した地点を「ユーザー確認済み」として記録しない。

責務を次の単位に分ける。名称は実装計画で既存命名に合わせて確定する。

| 単位 | 入力と出力 | 責務 |
| --- | --- | --- |
| Placesクライアント | 検索文字列またはPlace ID → 候補または分類済みAPIエラー | 認証、FieldMask、タイムアウト、Googleとの通信 |
| 訪問先解決サービス | 取引の店舗情報 → 特定結果または除外理由 | 表記正規化、限定した再検索、候補比較 |
| 軌跡作成サービス | 対象日と取引・軌跡のスナップショット → 保存予定内容と結果 | 適格性、時刻・順序、重複防止、既存訪問との統合 |
| Agentの完了処理 | 保存予定内容と実行トークン → 保存済みの応答 | 入力版の検証、軌跡と応答の原子的な保存 |
| 地点表示サービス | 保存済み地点参照 → 表示用座標と解決状態 | 座標期限、Place Detailsによる再取得、旧形式との互換 |

## 指示から保存までの流れ

1. 現在のユーザー発言が軌跡の作成・追加指示である場合に、専用処理を利用する。相談、検索だけの依頼、過去の発言や外部データに含まれる指示では保存しない。
2. 対象日の取引と既存の軌跡を読み、入力の版を保持する。日付はアプリの既存の日本時間に基づく日付抽出に合わせる。
3. 取引に記録された店舗名、支店名、住所から訪問先を検索する。店舗名は`merchant`を優先し、`title`に実際に書かれた店舗情報も利用できる。記録にない支店や所在地を生成しない。
4. 特定した訪問を時刻順に並べる。取引の推定時刻フラグは引き継ぐ。同時刻の場合は取引IDによる安定した順序とし、実際の前後関係が確定したとは表示しない。
5. 入力の版と実行トークンが有効なことを確かめ、軌跡と保存結果の応答を同じSQLiteトランザクションで保存する。
6. 保存完了後に件数、保存した訪問、除外した取引と理由を返す。保存前に「作成しました」と返さない。

応答には`trajectoryCreation`として、対象日、状態、新規保存・登録済み・除外の件数と各取引の結果を返す。状態は、新規保存があり除外がない`created`、新規保存と除外がある`partial`、新規保存がない`unchanged`、競合や保存エラーで書き込めない`failed`とする。設定エラーなどで全件未解決の場合も、`unchanged`と理由によって未保存と分かる表示にする。件数・状態・保存完了の文章はサーバーの確定結果から作り、LLMの自由な文章を保存成功の根拠にしない。

対象日が指示から一意に決まらない場合は、書き込みを行わず対象日の指定を求める。これは日付不足への応答であり、特定済みの日付や地点の承認要求にはしない。

## Google Placesによる検索

### APIと要求する情報

Text Search (New)の`POST https://places.googleapis.com/v1/places:searchText`を使用する。`languageCode`は`ja`とする。国内の住所が記録されている場合は`regionCode=JP`を利用するが、これを国内限定フィルターとして扱わない。海外と分かる入力を日本の候補に置き換えない。

FieldMaskは判定と表示に必要な範囲に限定する。基本の対象は`places.id`、`places.displayName`、`places.formattedAddress`、`places.addressComponents`、`places.location`、`places.types`、`places.googleMapsUri`、`places.attributions`。名前・住所・座標を含むためText Search Proの課金対象となる。レビュー、写真、営業時間、経路情報は要求しない。

`pageSize=10`とし、自動的な全ページ走査は行わない。物理的な所在地を持たないサービスエリア事業者を含めない。現在営業中かどうかで過去の訪問を除外する`openNow`フィルターは使わない。

### 柔軟な再検索と特定の条件

次の順で意味を保った検索を試す。重複する検索文字列は省く。

1. 記録にある店舗名・支店名と完全な住所。
2. 全半角、空白、ハイフン、一般的なブランド表記を正規化した店舗名と住所。
3. 店舗・支店名を維持し、住所の建物名や階数を外した検索。
4. 店舗・支店名と、入力に含まれる地域または所在地の識別情報。

検索から建物名や階数を外しても、元の住所を候補判定から削除しない。漢数字と数字による番地表記、郵便番号、丁目・番・号、建物・階数の記載差は、同じ所在地と説明できる範囲で正規化して比較する。

保存可能な候補は、有効なPlace IDと座標を持ち、店舗・支店の識別情報が一致し、入力に所在地がある場合はその主要な地域・番地情報にも矛盾がない候補とする。住所のみの一致や、ブランド名だけの一致では、別支店を選ばない。単なる住所地点を店舗の特定と扱わない。

支店名がない記録でも、店舗名と具体的な住所が一致して一意であれば特定できる。店舗名のみで所在地を絞れず複数の支店が残る場合は除外する。同一Place IDの重複候補はまとめる。別Place IDの同程度の適合候補が残る場合は`ambiguous`として除外する。LLMによる候補選択や、ユーザーへの候補選択要求には戻さない。

過去の訪問には現在のPlaces登録位置を利用する。その取引日時に同じ場所で営業していたことや、入口・売り場の位置まで証明されたとは扱わない。通常の説明としてその限界を表示できるが、保存条件やチェックボックスにはしない。

### 時間と呼び出し回数

同一の店舗・住所入力は一回の作成処理内で共有する。訪問先解決の同時実行数は3、個々のHTTPタイムアウトは8秒、検索全体の期限は120秒とする。既存のAgent全体の180秒期限内に保存と応答の時間を確保する。

一つの異なる検索入力に対するHTTP要求は最大4回とし、表記違いの再検索と一時的通信エラーの再試行を含む。特定できた時点で止める。429・5xx・通信エラーへの再試行は残り回数と全体期限の範囲で一回に限定し、長い`Retry-After`では待たず結果に理由を表示する。

取引件数自体による固定の切り捨ては行わない。期限までに特定できた訪問を保存し、未処理の取引は`budget_exceeded`として結果に残す。認証失敗、API未有効化などの設定エラーは再検索で解決しないため、検索を止めて設定エラーとして報告する。

## 保存、既存データ、再実行

訪問IDは対象日と取引IDからサーバーで決定的に生成する。Google地点の内部参照は、プロバイダーとPlace IDの組で識別する。一つの取引に対し、一つの自動作成訪問を保存する。別の取引による同じ店舗への訪問は、別イベントとして残す。

同じ`clientMessageId`への再送は既存の完了結果を返す。応答送信前の切断でも、再送によって二重保存しない。別のメッセージで同じ日を再作成する場合も、その日の同じ取引に紐づく既存訪問を再追加しない。既存訪問は結果の「登録済み」に分類し、残っている取引を検索する。先に除外された取引は、新しい指示で再検索できる。

既存の手動訪問はID、時刻、地点、根拠を保つ。新しいイベントを時刻順に統合する。隣接関係が変わらない移動区間は既存の情報を保ち、新たに接続が必要な区間は不明・推定として作る。元の移動手段や交通費の紐づきを、新しい区間の確定情報として転用しない。Google Directionsによる実経路の取得は今回の範囲に含めない。

取引の時刻・金額・店舗情報は、この作成処理によって変更しない。他の日の軌跡も変更しない。取引に結びついた古い訪問の更新や削除は、作成指示だけでは行わない。

特定済みの新規訪問がゼロの場合、既存日の削除・空の日への置き換えを行わない。結果だけを会話に保存する。

検索中に対象入力や軌跡が変更された場合、古い版の内容を保存しない。残り期限内に一度だけ最新状態から再準備できる。再準備で全体期限を延長しない。それでも競合する場合は未保存の結果を返す。技術的な競合を解決するために候補選択や保存承認を要求しない。

保存内容の検証、対象版の確認、実行トークンの確認、軌跡の書き込み、会話応答とターン完了の記録を原子的に行う。検索などの外部通信は書き込みトランザクションの外で実施する。期限切れやキャンセルされた実行は後から軌跡を保存できない。

## 地点の永続化と表示

GoogleのPlace IDは永続化する。訪問との関係、ユーザーの取引から得た店舗名・住所、解決方式、検索日時、除外理由も保存できる。

Googleから得た表示名・住所・候補本文は、そのまま恒久的な地点レコード、検索履歴、会話本文、変更案、ログにコピーしない。保存結果の表示名・住所は取引由来の情報を使う。Google表示情報が必要な画面では、その場で取得して帰属表示と共に表示する。検索処理の入力と出力の由来を区別する。

Google取得の緯度・経度は地点本体から分離したキャッシュに置き、取得日時と期限を持たせる。期限は最大30日とし、期限切れ座標は利用・配信しない。起動時、定期処理、関連読み出しで期限切れ行を削除する。長期間停止したアプリでは再起動時に削除してから利用する。バックアップや履歴JSONへGoogle座標を無期限に複製しない。

表示時に座標がなければPlace Details (New)で保存済みPlace IDの座標を取得する。失敗しても訪問記録は残し、地点を一時的に地図へ表示できない状態として返す。期限切れの座標、[0,0]、作り出した代替位置を使わない。取得できない区間は距離不明とする。

現在の`trajectory_places`は座標が必須なので、Google参照地点は座標なしでも存続できる形式へ移行する。旧地点には既存の座標と根拠を保持する。永続的な状態の版には地点参照と取引由来情報を含め、表示用キャッシュの更新だけでは版を変えない。

APIの表示用地点にはプロバイダー、解決状態、取得できた場合の座標を返す。変更検証は「旧形式の座標必須地点」と「Googleの参照地点」を区別する。旧提案や他の日の更新で状態を読み書きしても、Google取得情報を永続的な旧形式に変換しない。

## 地図と画面

軌跡の地図はGoogle Mapsへ切り替える。Google Placesの結果をMapbox上に表示しない。旧Mapboxコンポーネントのコードは保存し、既存の旧地点もGoogle Maps上で表示する。

Google Maps JavaScript API用のブラウザキーは別設定`GOOGLE_MAPS_BROWSER_API_KEY`で読み、公開設定にはこのキーだけを出す。ブラウザキーはHTTPリファラーとMaps JavaScript APIに制限する。`GOOGLE_PLACES_API_KEY`はサーバー専用とし、公開設定、JavaScript、例外メッセージ、ログに出さない。

ブラウザキーの未設定、地図スクリプトの読み込み失敗、座標の再取得失敗があっても、訪問一覧と作成結果は表示できる。Places側の保存処理を地図設定の不足で止めない。地図が表示できない場合は理由と再試行操作を表示し、Mapboxへ切り替えてGoogle座標を表示しない。

Google Mapsの帰属表示を隠さず、必要な第三者帰属も表示する。地図なしでGoogle由来情報を表示する箇所にはGoogle Mapsの帰属を付ける。必要な利用規約・プライバシー説明へのリンクをアプリの設定・説明画面に設け、Googleへ送信する店舗名・住所情報について説明する。

Agent Chatの作成結果は承認カードではなく、保存済み結果として表示する。最低限の構造は以下とする。

- 対象日、処理状態、新規保存件数、登録済み件数、除外件数。
- 保存した訪問の取引由来の名称と時刻、推定時刻の表示。
- 除外した取引の名称・時刻と、利用者が分かる理由。
- 作成した日の軌跡を開くリンク。

例: 「10月1日の軌跡を作成しました。2件保存、1件除外。○○店: 同名の候補が複数あり、店舗を特定できませんでした。」

長い結果は除外一覧を折りたためるが、除外件数は常に表示する。スマートフォンでも名前と理由を読める。処理中、保存済み、一部保存、未保存を区別し、旧来の内部バリデーション文言をそのまま利用者に出さない。

この画面はアプリ内画面として扱う。見た目は`DESIGN.md`、一般的なUXは`design-system/household-budget-app/MASTER.md`、操作・アクセシビリティは`ui-ux-pro-max`に従う。ダッシュボードの構成変更は行わない。

## 除外とエラー

| コード | 表示する理由 | 保存への影響 |
| --- | --- | --- |
| `not_visit` | 収入、明示されたオンライン取引など、実店舗の訪問を示す記録ではない | その取引を除外 |
| `insufficient_identity` | 店舗・所在地を特定する情報が不足している | その取引を除外 |
| `not_found` | 条件に合う店舗が見つからない | その取引を除外 |
| `ambiguous` | 複数候補が残り一つに特定できない | その取引を除外 |
| `identity_mismatch` | 候補の店舗・支店または住所が記録と合わない | その取引を除外 |
| `missing_coordinates` | 候補に有効な座標がない | その取引を除外 |
| `provider_unavailable` | 通信エラー・利用上限などで検索できない | 特定済み訪問は保存し、残りを理由付きで除外 |
| `budget_exceeded` | 処理時間内に検索を完了できなかった | 特定済み訪問は保存し、残りを理由付きで除外 |
| `provider_configuration` | APIキー、API有効化、権限などの設定に問題がある | 未解決の検索を止める。特定済み訪問があれば保存 |
| `source_conflict` | 検索中に対象データが変更され、安全に保存できなかった | 再準備でも解決できなければ軌跡を書き込まない |
| `save_failed` | 保存を完了できなかった | 原子的にロールバックし、保存済みと表示しない |

API障害を「店舗が見つからない」として扱わない。分類コードは機械可読な結果に含め、日本語の理由を画面に出す。除外対象には元の取引IDを内部的に保持する。結果は会話を開き直しても復元できる。

## 旧検索経路と今回の範囲

Geolonia、Web検索、公開ページ抽出、関連する検索履歴コード、テスト、既存の根拠表示を削除しない。通常のAgentツール登録と地点検索サービスの有効な依存関係をGoogleに切り替える。Google失敗時に旧プロバイダーへフォールバックしない。

新しい汎用地点検索もGoogleを使用する。検索だけの依頼では検索結果を返すだけで軌跡を書き込まない。過去の検索履歴は参照可能な履歴として残し、新しい作成の地点判定には流用しない。

既存の保留中の変更案は新しい設定によって自動承認しない。旧候補への新たなGeolonia・Web検索も行わない。新しい作成指示は専用処理へ進む。

この変更で追加確認を廃止する範囲は、取引からの軌跡作成・追加である。取引の編集、レシート登録、軌跡削除などの既存の承認方針を一括で変更しない。既存の未コミットの訪問ID検証・ツールエラー回復修正は保持する。

## 受け入れ条件と検証

1. 指定日を含む作成指示から保存まで完了し、候補・位置・順序・変更案の確認操作が一つも必要ない。
2. 特定できた候補と曖昧な候補が混在する場合、特定できた訪問だけ保存し、除外した取引と理由を応答と履歴に表示する。
3. 店舗名・支店名・住所の表記差を試せる。同ブランドの別支店や、住所だけ一致する候補を保存しない。
4. 全件除外、対象日の取引ゼロ、API設定不備でも既存の軌跡を削除しない。未保存と保存済みを正しく表示する。
5. 同じメッセージの再送、同じ日の新しい作成指示、保存直後の通信切断で重複を作らない。手動訪問と対象外の日を保護する。
6. 競合、ターン期限切れ、保存エラーで一部の書き込みだけが残らず、保存後に応答だけ失われても再送で保存済み結果を返せる。
7. Google座標の期限切れ後は削除・再取得し、失敗しても訪問は残る。表示用キャッシュ更新で提案や入力版に不要な競合を起こさない。
8. Google地点を含む状態の読み出し・変更・旧形式との混在で、Google座標や表示情報を恒久保存し直さない。
9. 通常の検索と作成にGeolonia・Web検索が一度も呼ばれないことを検証する。旧コードが残っていることも確認する。
10. Google Maps上で旧・新地点が表示でき、地図キー未設定時も一覧・結果を読める。公開設定やログにサーバー用キーが出ない。

検証は、候補判定の単体テスト、外部APIを置き換えたAgent・SQLite統合テスト、Agent Chatと軌跡画面のブラウザテストで行う。承認操作なしの保存を実際のDB変更で確かめる。ブラウザ確認はデスクトップと電話幅で行う。

実APIでは、ルート`.env`を使った読み取り専用の検索によりPlaces API (New)の利用可否と代表店舗の応答を確認する。軌跡の実保存は一時DBで検証し、利用者の取引や既存軌跡を検証のために書き換えない。API有効化、課金設定、キー制限は存在確認だけでは保証されておらず、実装時に接続結果で確かめる。ブラウザキーの準備状況は別に確認する。

以下は2026-10-04に確認した一次資料。実装時も必要なAPI仕様を公式資料で確認する。

- [Text Search (New)](https://developers.google.com/maps/documentation/places/web-service/text-search): エンドポイント、FieldMask、言語、結果件数、物理所在地フィルター、課金区分。
- [Places API policies](https://developers.google.com/maps/documentation/places/web-service/policies): Place ID、帰属表示、利用規約・プライバシー説明。
- [Google Maps Platform Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms): Placesの地図利用制約と緯度・経度の30日キャッシュ例外。
- [API security best practices](https://developers.google.com/maps/api-security-best-practices): サーバー用キーの保護、用途ごとのキー、ブラウザの制限。

日本での利用を前提に一般のPlaces API条件に合わせた設計とする。請求先がEEAで異なる条件が適用される場合は、実装時にその条件を確認して対応する。Googleの表示名・住所など全データに30日保存を許す設計ではない。
