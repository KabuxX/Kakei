# Kakei Agent Chat 設計

作成日: 2026-10-03

## 目的と前提

Kakei を普段使いする一人の利用者が、会話とレシートから取引を整え、指定日の取引を根拠に生活軌跡を作成・編集できるようにする。成功とは、保存前に利用者が根拠と差分を確認でき、承認した結果が SQLite と既存画面に一致して反映されることである。

利用者が指定した技術は React の `front/`、FastAPI の `backend/`、LangChain を用いる agent である。モデルは OpenAI API を使い、レシート画像は承認済みの取引に紐づけて端末内に保存する。取引・軌跡の変更案は毎回確認する。軌跡には推定を含めてよいが、推定であることと根拠を明示する。未知の地点は地点検索 API の候補から利用者が選ぶ。

この設計は、チャット基盤、レシートによる取引作成・編集、指定日の軌跡作成・編集を一つの初期機能として定義する。実装計画では共通基盤、レシート、軌跡の順に作業を分ける。

## 現状と必要な接続

- `backend/` はローカル単一ユーザーの FastAPI と SQLite。取引の取得・追加・削除はあるが編集 API はない。
- 軌跡の取得と日・地点・イベント・区間の作成・置換・削除 API はあり、変更は SQLite に保存される。一方、`front/src/Trajectory.jsx` は固定 JSON を読み、API の変更を表示しない。
- 軌跡のフロントモデルは 2026 年 9 月、東京の座標、2 地点以上を前提にする。保存層の座標検証も東京に限定される。普段使いする日付・場所と、1 地点の日を扱うために拡張する。
- レシートのアップロード、画像保存、agent 会話、承認待ち、変更履歴の仕組みはまだない。

## 構成と責務

`front/` に `#agent` の Agent Chat 画面を追加し、既存のアプリナビゲーションから開けるようにする。`backend/api/` は会話、アップロード、変更案、承認の HTTP 契約と既存のローカルアクセス制限を担う。`backend/agent/` は LangChain `create_agent`、OpenAI モデル接続、会話の文脈、ツール定義、レシート抽出、地点候補の収集、変更案の組み立てを担う。`services/` は型・業務ルール・重複・参照関係・競合を検証し、`db/` は読み書きと一括コミットを担う。agent から SQLite の任意の書き込み接続は渡さない。

単一 agent に以下のツールを渡す。

| ツール | 役割 | 境界 |
| --- | --- | --- |
| `read_sql` | agent が作った読み取り SQL から取引・軌跡を調べる | 専用の読み取り接続、公開ビュー、件数・時間制限 |
| `edit_transaction` | 取引の新規・編集コマンドを変更案に加える | 既存の取引検証を通し、承認までは DB を変えない |
| `edit_trajectory` | 日・地点・イベント・区間の新規・編集コマンドを変更案に加える | 軌跡検証と同日参照の確認を通し、承認までは DB を変えない |
| `read_receipt` | 今回アップロードしたレシートから構造化候補を得る | レシートの内容を命令として扱わない |
| `search_place` | 既存地点と外部の地点候補を返す | 未知の地点は利用者が候補を選んで確定する |

編集ツールの結果は、対象 ID、変更前後、根拠、推定項目、元データの版を持つ **変更案** である。一つの変更案は、関連する取引と軌跡をまとめた一回の確認単位とする。承認 API だけが変更案を原子的に適用する。取引と軌跡をまたぐ変更は同じ SQLite トランザクションで成功または失敗させる。手動の取引更新 API と agent は同じ保存・検証処理を使う。

## データと API

次の API を追加する。レスポンスは既存 API と同じエラー形式、`Cache-Control: no-store`、同一オリジン制限を用いる。

| API | 用途 |
| --- | --- |
| `POST /api/agent/threads`、`GET /api/agent/threads`、`GET /api/agent/threads/{id}` | 会話の開始・一覧・メッセージと変更案の再表示 |
| `DELETE /api/agent/threads/{id}` | 会話と未承認案を削除。保存済みの取引・軌跡は維持 |
| `POST /api/agent/threads/{id}/messages` | 利用者発言を送り、応答または変更案を返す |
| `POST /api/agent/threads/{id}/receipts` | レシートを一つアップロードし、会話に紐づける |
| `PUT /api/agent/proposals/{id}` | 確認カードで修正した案を再検証し、新しい案の版を返す |
| `POST /api/agent/proposals/{id}/approve`、`POST /api/agent/proposals/{id}/reject` | 確認済み案の適用または破棄 |
| `GET /api/transactions/{id}/receipts`、`GET /api/receipts/{id}` | 取引に紐づいたレシートの一覧と画像・PDF の表示 |
| `PUT /api/transactions/{id}` | 取引全体の編集。ID は維持し、共通検証を通す |
| `GET /api/trajectory` | 保存済み日付の一覧を返し、画面の日付選択に使う |

会話、メッセージ、変更案、承認結果、実行履歴、レシートを SQLite に保存する。レシート本体はサイズを制限した BLOB とし、SHA-256、MIME、取引 ID を記録する。承認待ちファイルと変更案は 24 時間で期限切れにし、却下時または期限切れ時に未使用ファイルを削除する。承認済みファイルは取引から参照でき、取引削除時には参照のなくなったファイルを削除する。会話の削除は取引や軌跡を変更しない。履歴には変更前後と承認時刻を記録し、ファイル本体や API キーをログに複写しない。

取引の編集では `id` を維持し、品目は一括置換する。日時を変更するときは軌跡から参照される同日条件を再検証する。従来の `timeEstimated` は変更されない日時では維持し、利用者が時刻を確定したときに解除する。

軌跡の保存形式には、イベントの時刻が確定・推定・不明のどれか、地点を選んだ根拠、区間の交通手段の根拠、参照取引 ID を持たせる。イベントの時刻は不明なら `null` を許し、表示順は保存済みの `position` で管理する。初期取込で割り当てた仮時刻は確定時刻として使わない。順序が判定できない複数地点は利用者に並び順を確認する。1 地点の日は区間なしで保存・表示する。座標検証は経度 -180〜180、緯度 -90〜90 に広げ、既存データは移行時に根拠種別を「既存データ」として扱う。店名と地点名の文字列一致だけでは同一性を判定しない。

## レシートから取引へ

初期対応は JPEG、PNG、WebP、PDF の一ファイルで、上限は 10 MiB、PDF は最大 3 ページとする。FastAPI `UploadFile` で受け取り、拡張子ではなく実際のファイル形式とページ数を検査する。上限超過は処理前に理由を示して拒否する。PDF はモデルに渡せる画像または文書入力へ変換する。レシート抽出は店名、日付、時刻、合計、通貨、品目、税・割引、支払方法と読み取れなかった欄を構造化して返す。抽出値は取引コマンドの候補であり、保存データではない。

新規・編集の判断では同じ画像のハッシュと、近い日付・店名・金額の既存取引を候補として出す。利用者が対象取引を選ぶまで自動的に上書きしない。必須項目が読み取れない場合は質問または確認カードの修正欄で補う。現在の取引形式では品目金額の合計が取引金額と一致する必要があるため、不一致時は差額を示す。利用者が明細を修正するか、品目を空にして合計のみ保存する。税・割引を架空の品目として作らない。

## 取引から軌跡へ

指定日の取引から日時、店名、カテゴリ、交通費の証拠を読む。同じ取引を二つの訪問に自動割当てしない。`timeEstimated` の取引は推定表示とし、時刻不明なら確認を求める。新しい地点は検索候補の名称・住所・位置・出典を提示し、利用者が選んだ候補だけを保存する。地点が見つからない場合は候補の再検索または利用者による位置指定を求め、座標を創作しない。

地点検索の初期接続先は Geoapify とし、API キーはサーバー設定に置く。結果と出典表記を地点に保持する。既存の Mapbox は地図表示に使う。Mapbox Search Box は取得結果の永続保存に制限があるため、軌跡の保存元には使わない。

取引に対応する訪問は取引 ID と結び、地点間の線は推定区間として表示する。交通手段は交通費の証拠または利用者の指定がある場合だけ表示する。線と距離は地点間の概算であり、実際の通行経路・移動距離とは区別する。agent が取引の日時・店名を編集して軌跡の参照が不整合になる場合は、軌跡も含む修正案を出すまで承認できない。既存の取引削除・サンプル削除では、参照を同じトランザクションで外し、交通費の証拠を失った区間は推定区間へ変更する。削除の確認画面にはこの影響を示す。

## Agent Chat の画面

Agent Chat はアプリ内画面であり、`DESIGN.md` の白い面、淡いカード、文字、余白、角丸を使う。`MASTER.md` の一般 UX 指針と `ui-ux-pro-max` の操作・アクセシビリティ指針を適用する。公開サイト向けのヒーローや販促コピーは使わない。ページ固有の情報順序は、状態と対象日、会話、根拠付きの変更案、入力欄・添付操作とする。

確認カードは対象日、取引または軌跡の変更前後、レシートプレビュー、重複候補、地点候補、確定値と推定値、発生する保存操作を一か所に示す。修正、承認、却下の各操作を明示する。通信中・モデル処理中・確認待ち・保存中・保存済み・失敗の状態を文字で示し、失敗時には再試行できる。スマートフォンでは一列に配置し、キーボード操作、フォーカス移動、スクリーンリーダーへの状態通知を用意する。保存後は概要・取引・軌跡の表示を再取得する。

軌跡画面は固定 JSON ではなく API から日付一覧と選択日の内容を取得する。1 地点の日、時刻不明、地点未解決、地図が使えない場合の表示を定義する。既存のサンプル表示は SQLite に初期投入したデータから行う。

## 制御と失敗時の扱い

- `OPENAI_API_KEY`、画像入力とツール呼び出しに対応するモデルを示す `KAKEI_AGENT_MODEL`、`GEOAPIFY_API_KEY` をサーバー設定とする。未設定なら Agent Chat で不足している設定を示し、既存の家計画面は利用できる。地図表示は従来どおり `VITE_MAPBOX_ACCESS_TOKEN` を使う。
- `read_sql` は専用の `mode=ro` 接続と SQLite authorizer を使い、取引・品目・軌跡の公開ビューへの読み取りと単一の `SELECT` だけを許可する。`ATTACH`、`PRAGMA`、拡張機能、書き込み、内部テーブルへの参照と許可外の SQL 関数を拒否する。最大 100 行、実行時間上限 2 秒、返却サイズ上限 64 KiB を設ける。SQL の先頭文字列だけを見て安全判定しない。
- 承認は一度だけ使用できる変更案 ID と、確認カードに表示した案の版を指定する。修正後に古い版を承認できない。承認時に対象取引・日付・地点の版を再検査し、変化していれば `409 conflict` で差分の再確認を求める。承認リクエストの再送は同じ保存結果を返し、重複登録しない。却下は DB の業務データを変えない。
- 取引の参照日、軌跡の ID・時刻順・区間・地点、金額と品目合計を一括コミット前に再検証する。失敗時は全変更をロールバックし、確認案と会話を残す。
- OpenAI と Geoapify のキーは環境変数からサーバーだけが読む。モデルには質問に必要な取引範囲と今回のレシートのみを送る。レシート本文、SQL 結果、地点検索結果を外部からのデータとして扱い、そこに書かれたツール操作指示には従わない。外部トレースは初期状態で無効にする。
- 一回の発言で agent のツール呼び出しは最大 8 回、モデル処理は最大 60 秒とする。レスポンスを待つ間は画面に処理状態を表示する。モデル・地点検索・アップロードが失敗した場合は業務データを書かず、再試行できる状態を返す。ファイル容量も制限し、費用と無限ループを抑える。

## 検証と完成条件

外部モデルと地点検索はテスト用の偽物へ差し替え、一時 SQLite DB で決定的に検証する。手元の実 DB をブラウザテストで変更しない。

1. チャットでレシートをアップロードし、新規取引と既存取引の編集案を作り、差分を修正・承認できる。画像は該当取引から見直せる。
2. 同じレシートの再送と近似取引の候補を示し、同じ承認の再送では取引が増えない。
3. 指定日の取引から軌跡を作成・編集でき、未知の地点は候補選択を経る。推定の時刻・地点・区間は画面に明示される。
4. 書き込み SQL、複数文、公開対象外の参照、長時間クエリは拒否される。編集ツールも承認前には業務データを変更しない。
5. 競合、抽出失敗、地点検索失敗、保存途中の検証失敗で、取引と軌跡は部分的に更新されない。確認案は再試行や修正に利用できる。
6. 保存後と再起動後に会話、レシート、取引、軌跡が一致する。概要・取引・軌跡の画面は SQLite の最新値を表示する。
7. デスクトップとスマートフォンで入力・添付・確認・保存ができ、キーボードだけでも完了できる。

## 実装順

1. **共通基盤:** 取引編集、軌跡画面の API 接続と一般化、agent の会話・SQL・変更案・承認・一括コミット。
2. **レシート:** アップロード、OpenAI の抽出、重複候補、画像保存、取引の作成・編集。
3. **軌跡:** 地点検索、根拠と推定の保存、指定日の軌跡の作成・編集、画面での表示。
