# React によるフロントエンド置き換え

## 目的と完成条件

Kakei の `front/` を React に置き換える。利用者に見える画面、文言、配置、操作、URL、保存データの扱いは現行版と同じにする。目的は画面の状態と表示をコンポーネント単位で管理できる構成にすることであり、新機能やデザイン変更は含めない。

普段の起動は引き続き FastAPI のコマンドだけで完結し、`http://localhost:8765/` で画面と API を同じオリジンから利用できる。初回のブラウザ保存データ取り込みと、その後の SQLite 保存は維持する。

## 配信構成

- `front/src/` に React の画面、状態管理、API クライアント、取引データの純粋関数を置く。React と React DOM を使い、Vite で静的ファイルを生成する。
- `front/index.html` は React のマウント先と必要なメタ情報を持つ。既存の SVG アイコン、クラス名、要素の順序、`front/styles.css` は画面を照合しながら移す。
- ビルド成果物 `front/dist/` をリポジトリに含める。FastAPI の既定の静的配信先を `front/dist/` に切り替える。利用者は Node.js や Vite を起動せず、既存の `fastapi run backend/server.py --host 127.0.0.1 --port 8765` だけで使える。
- 開発者はソース変更後に依存関係を固定した lockfile からインストールし、ビルドを更新する。生成物とソースの整合を検査する。
- API のパス、JSON の形式、ポート、SQLite の保存先は変更しない。`backend/server.py` の `create_app(db_path, front_dir)` によるテスト用の配信先指定は残す。

## 画面と状態

アプリ画面を共通シェル、ダッシュボード、取引詳細、取引追加ダイアログに分ける。ダッシュボード内の月次収支、予算、カテゴリ内訳、週次支出、取引履歴は表示用コンポーネントとし、現行の DOM と CSS セレクタに対応する構造を維持する。

React が取引一覧、表示月、検索語、種別フィルタ、ハッシュ URL、ダイアログの入力値、通信中・失敗状態、通知を管理する。取引一覧の正本はサーバーであり、書き込み後とタブが再表示されたときは API から再取得する。初期化時だけ既存の `kakei-transactions-v1` を読み、存在しないときだけサンプルを作る。ブラウザ保存領域への取引の再書き込みはしない。

既存の `#overview`、`#transactions`、`#budget`、`#insights`、`#transaction/{id}` の意味と ID のエンコードを維持する。取引詳細から一覧へ戻る際のスクロール位置とフォーカス、画面遷移後の見出しフォーカス、ダイアログの開閉と入力フォーカスを引き継ぐ。ルーティング専用の外部ライブラリは導入しない。

## 失敗時と入力時の動作

初回読み込みの失敗、再取得の失敗、保存・削除の失敗を現行と同じ画面で案内する。書き込みは成功し、その後の再取得だけが失敗した場合は再書き込みを促さず「表示を再読み込み」を提示し、重複操作を防ぐ。通信中と再取得が必要な間は該当する操作を無効にする。

取引追加フォームは収入・支出の切替、品目合計と手入力金額の切替、フィールド別のエラー、サーバーの検証エラー表示を維持する。ダイアログはキーボードで閉じられ、フォーカスが開いた操作へ戻る。表示の切替とエラー通知は意味のある HTML と適切なライブ領域で伝える。

## 見た目と UX の基準

対象は公開マーケティングページではなく、家計管理のアプリ画面である。`DESIGN.md` を色、文字、角丸、影などの見た目に適用し、`design-system/household-budget-app/pages/dashboard.md` をダッシュボードの順序と密度に適用する。`MASTER.md` と `ui-ux-pro-max` は残る UX、アクセシビリティ、操作の確認に用いる。移行を理由に新しい視覚スタイルを追加しない。

デスクトップと電話幅の双方で、アプリナビゲーション直後に対象月と収支状態、または記録操作が見えることを維持する。チャートは数値のテキスト表現とアクセシブルな名前を維持し、色だけで意味を伝えない。

## 検証

1. 変更前の画面を、固定した取引データと日付でデスクトップ幅と 375px 幅に記録する。主要な状態として読み込み中、通常表示、空の月、取引詳細、追加ダイアログ、通信エラーを押さえる。
2. 既存の取引データ、CSV、API 契約のテストを移行後も実行できる形にする。React の画面テストで月切替、検索、詳細 URL、フォーム、初回取り込み、追加・削除、失敗と再試行を確認する。
3. ビルド後の FastAPI 起動で、同一オリジンの画面と API、初回取り込み、SQLite への保存をブラウザから確認する。
4. 変更前後の画面を同じビューポートとデータで比較する。デスクトップと電話幅の最初の表示領域、スクロール位置、キーボード操作、ダイアログのフォーカス、水平スクロールの有無を確認する。
5. ビルド成果物がソースに対応し、クリーンなチェックアウトで Python 依存を導入した後は FastAPI の起動コマンドだけで画面が表示されることを確認する。
