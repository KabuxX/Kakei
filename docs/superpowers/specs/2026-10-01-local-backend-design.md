# Kakei ローカルバックエンド設計

## 目的と完成条件

既存の家計ダッシュボードで扱う取引を、ブラウザ内だけでなくローカルのサーバーへ保存する。現在の `http://localhost:8765/` を維持し、既存の `localStorage` にある取引を初回に引き継ぐ。利用者は当面一人で、ログインと利用者ごとのデータ分離は設けない。

完成時には、画面から取引を追加・表示・削除し、サーバーを再起動しても同じ内容を確認できる。月別の収支・カテゴリ内訳・週別支出・固定予算・検索・詳細URL・CSV出力・サンプル削除は、現在の意味と操作を保つ。取引編集、予算編集、外部公開、同期サービスは対象外とする。

## 構成と実装境界

- Python 3.9 の標準ライブラリを使う。`http.server` が `front/` の静的ファイルと `/api/` を同じオリジンから配信し、`sqlite3` が取引を永続化する。追加の Python パッケージは使わない。
- サーバーは既定で `127.0.0.1:8765` にバインドする。ブラウザで開く案内は、既存の保存領域と一致する `http://localhost:8765/` とする。画面は `file://` から直接開く運用を対象外とする。
- バックエンドの製品コード、DB初期化、バックエンドのテストはすべて `backend/` に置く。SQLiteファイルは既定で `backend/data/kakei.sqlite3` に作成し、Gitの対象から除く。起動は `python3 backend/server.py` とし、必要なら `--db PATH` で保存先を指定できる。テストでは一時DBを使う。
- `front/` ではAPI呼び出しと読み込み状態の表示を追加し、既存の集計・描画・フォーム検証を活用する。`front/` の画面は公開マーケティングページではなくアプリ内画面である。情報順序は `design-system/household-budget-app/pages/dashboard.md`、見た目は `DESIGN.md`、残る一般UXは `MASTER.md` に従う。
- カテゴリと月額予算は現在の固定値を維持する。サーバーは新規取引のカテゴリを既存の選択肢に照らして検証するが、集計やCSVの生成は画面側に置く。UIにない編集APIや集計APIは追加しない。

## API契約

すべてのAPIは JSON を返す。エラーは `{ "error": { "code": "...", "message": "...", "field": "..." } }` とし、`field` は入力欄に対応する場合だけ付ける。作成・初期化は `Content-Type: application/json` を必須とする。JSONはUTF-8。取引のフィールド名は既存画面の `id`、`title`、`amount`、`date`、`type`、`category`、`merchant`、`paymentMethod`、`items` に合わせる。

| 操作 | 応答 | 用途 |
| --- | --- | --- |
| `GET /api/status` | `200 { "initialized": boolean }` | 初回取り込みの要否を判定する。 |
| `POST /api/initialize`、本文 `{ "transactions": [...] }` | `201 { "count": number }`、初期化済みなら `409` | 未初期化DBに取引配列を一度だけ取り込む。空配列も有効。 |
| `GET /api/transactions` | `200 { "transactions": [...] }` | ダッシュボード、検索、CSVの元データを取得する。 |
| `GET /api/transactions/{id}` | `200 { "transaction": {...} }`、未発見なら `404` | 詳細URLから一件を取得できるようにする。 |
| `POST /api/transactions`、本文に取引の入力項目 | `201 { "transaction": {...} }` | IDはサーバーが生成して返す。 |
| `DELETE /api/transactions/{id}` | `204`、未発見なら `404` | 詳細画面で確認後、一件を削除する。 |
| `DELETE /api/samples` | `200 { "deletedCount": number }` | `sample-` IDの取引だけを一括削除する。 |

初期化前は `status` と `initialize` 以外のAPIを `409 not_initialized` とする。初期化後の再取り込みは拒否し、既存のサーバーデータを上書きしない。取引一覧は日付の降順、同日の場合はIDの降順で返す。URLのIDは安全にデコードし、既存の `#transaction/<encoded-id>` 形式を維持する。新しい取引はサーバー生成の衝突しないIDを使用する。不正なJSONや入力は `400`、存在しない取引は `404`、対象外のHTTPメソッドは `405`、本文サイズ超過は `413`、DB障害は `500` とする。

## データの検証と保存

新規取引では、空白を除いた1〜60文字の内容、実在する `YYYY-MM-DD` の日付、`income` または `expense`、1円から999,999,999円までの整数金額、対応するカテゴリを検証する。収入カテゴリは「収入」、支出カテゴリは画面の6種類とする。支出には1〜60文字の店名・取引先と4種類の支払方法を必須とし、品目がある場合は各品目の1〜60文字の名前と整数金額を検証して合計が取引金額と一致することを要求する。収入は支出専用項目を持たない。新規取引の本文は64KiB、初回取り込みは8MiBまでとする。

初回取り込みでは既存レコードのIDを維持し、必須の取引項目を全件検証する。旧形式の支出で店名・支払方法・品目がない場合も取引を受け入れる。任意の詳細項目が不正な場合は、現在の `readExpenseDetails` と同じように、その項目だけを未登録として扱い、取引自体は失わない。例えば品目の合計が取引額と異なる場合は品目だけを空にする。重複IDや必須項目が不正な場合は全件を拒否し、どの配列位置とIDが原因かを応答で示す。画面は元の `localStorage` をそのまま保持し、取り込み失敗を表示する。

SQLiteには `transactions` テーブル（ID主キー、日付、種別、内容、カテゴリ、金額、任意の店名・支払方法・品目JSON）と、初期化済みフラグを持つ `meta` テーブルを置く。初期化、追加、削除、サンプル一括削除はそれぞれ一つのDBトランザクションで行う。DB書き込みが失敗した場合は途中結果を画面へ成功として返さない。

## 初回取り込みと画面のデータフロー

1. 画面は起動時に表示月を示し、サーバーの状態を取得する。
2. DBが未初期化なら、同じオリジンの `kakei-transactions-v1` を読む。キーが存在すれば、空配列を含め、その内容を `POST /api/initialize` へ送る。キーが存在しないときだけ、現在のサンプル生成処理で前月のサンプルを作って送る。ブラウザの保存領域を読めない場合は初期化せず、エラーを表示する。
3. 初期化が成功した後、または既に初期化済みの場合は、取引一覧を取得して画面を描画する。初期化競合で `409` が返った場合も一覧を再取得する。
4. 以後の追加・削除・サンプル削除では、API成功後に一覧を再取得してから画面内の配列と集計を更新する。失敗時は入力内容と表示中の取引を保持する。詳細画面への直接アクセスはデータ取得後に該当IDを表示する。
5. 別タブから戻った際はサーバーから再取得する。月・検索語・種別フィルターなどの画面内状態は保持する。CSVは再取得済みの選択月の取引から生成する。

既存の `localStorage` は取り込み後も削除せず、移行元のスナップショットとして残す。ただし、以後の正しい保存先はSQLiteであり、旧スナップショットは新規取引に追随しない。DBを削除して初期化し直す場合、この古いスナップショットが再び候補になることを起動手順に明記する。

## 読み込み・失敗・ローカルアクセス

初回ロード中に0円を確定した収支として見せない。ダッシュボードの最初の領域には選択月と読み込み状態を表示する。読み込み失敗時には同じ領域で再試行操作と理由を示し、追加・削除を成功したように扱わない。初回取り込みのJSONが壊れている場合はサンプルで上書きせず、旧データを保持して修正可能なエラーを示す。追加の通信失敗ではフォームを開いたままにし、削除の通信失敗では詳細を維持する。

サーバーはループバック以外で待ち受けない。静的ファイルの参照は `front/` 内に制限し、ディレクトリトラバーサルを拒否する。書き込みAPIは同じオリジンのリクエストのみ受け、他サイトからの書き込みを拒否する。CORSは有効にしない。これらはローカル専用の境界であり、インターネット公開や複数利用者での利用を許可する設計ではない。

## テストと完成確認

- Pythonのテストで、初期化の一回性と空配列、旧形式、任意詳細の補正、全件検証の原子性、追加・取得・削除、サンプル削除、DB再接続後の永続化、APIエラーと静的ファイルのパス制限を確認する。
- 既存の JavaScript テストを実行し、フォーム入力、詳細URL、CSVに影響がないことを確認する。
- ブラウザで既存の `http://localhost:8765/` に保存した取引を取り込み、再読み込みとサーバー再起動後も一致することを確認する。月切り替え、検索、取引詳細の直接URL、追加、削除、サンプル削除、CSV、別タブから戻ったときの更新、通信失敗時の再試行も確認する。
- デスクトップ幅とスマートフォン幅で、アプリナビゲーション直後に選択月と収支、または読み込み・再試行の状態が見えることを確認する。ブラウザプレビューが利用できない場合は描画構造を検査し、その制限を報告する。
