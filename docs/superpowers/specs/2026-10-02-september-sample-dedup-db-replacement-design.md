# 2026年9月サンプルの重複整理と SQLite 置換 — 設計

## 目的と確認できる状態

新しい9月サンプルから、日付と ID だけが違う同内容の取引を削除する。同内容が複数日ある場合は最新日の1件を残す。軌跡は残った取引から説明できる日と地点だけを表示する。既存の backend SQLite に保存されている旧サンプル16件を整理後の新サンプルで置き換え、概要と軌跡のデータを揃える。

利用者が登録したサンプル以外の取引は保存する。旧サンプル16件の記録ファイル `front/src/data/old-samples.json` は変更しない。mock API と backend API の操作・レスポンス契約は変更しない。

## 現状と今回の変更範囲

- `front/src/data/september-transactions.json` は103件、30日分。同じ日の完全重複と重複 ID はない。日付・ID を除く全内容が同じ反復は34種類、反復に含まれる取引は100件である。
- `front/src/data/september-timeline.json` は30日分の地点、イベント、区間を持つ。現行の表示モデルは取引 ID と日付の一致を要求する。
- ローカルの `backend/data/kakei.sqlite3` は初期化済みで、旧 JSON と ID・主要項目が一致する旧サンプル16件だけを持つ。現在のファイルには軌跡テーブルがまだない。
- 従来の設計書にある「30日すべて」「既存 DB は変更しない」という条件は、この依頼に限って本設計の決定で置き換える。旧 JSON を独立して保存する条件は維持する。

## 取引 JSON の整理

重複判定キーは `type`、`title`、`category`、`amount`、`merchant`、`paymentMethod`、および順序を含む `items` の品目名・金額で構成する。`id` と `date` だけを比較から除く。JSON の項目順や空白は比較に影響させない。同じキーの取引は日付が最も新しい1件だけ残し、元の ID と内容は変更しない。選択結果は37件となる。旧 JSON と一致する `sample-0` は、別日で重複した取引ではないため新 JSON に残る。

整理結果は `september-transactions.json` に保存する。新規初期化と Vite mock API は引き続きこの JSON を読み込む。旧 JSON と mock API の処理は変更しない。取引の品目合計、ID の一意性、参照日付を検証する。

## 軌跡 JSON と画面

残した取引を参照するイベントは保持し、削除した取引を参照するイベントは削除する。取引 ID のない駅などのイベントは、残した交通取引を根拠にする区間の端点として必要な場合に保持する。根拠のない駅イベントは削除する。取引に結び付くイベントが2件以上残る日だけを軌跡 JSON に残す。この規則では9月19〜30日の12日が残る。

残ったイベントを時刻順に接続する。元の区間が残った隣接イベントを直接つないでいれば、その区間の経由地点と徒歩の推定表示を保持する。電車・バス表示は対応する交通取引が残る場合だけ保持する。イベントの削除によって新しく隣接する地点間は、交通手段と経由地点を断定せず「移動（推定）」の区間にする。全ての `transactionId` と `transportTransactionId` は新しい取引 JSON 内の同じ日付の ID を指す。地点カタログは残ったイベント・区間から参照される地点に絞る。

軌跡画面は JSON に存在する12日だけを日付選択に表示する。前後ボタンは暦の連続日を意味しない「前の記録日」「次の記録日」とし、選択可能な日を移動する。地図、時系列、集計は整理後の JSON から計算する。見た目は既存のアプリ内画面と `DESIGN.md` に従い、地図以外でも地点と取引の関係を読めるようにする。概要ページのレイアウトは変更しない。

## SQLite の一度限りの置換

ローカル DB の更新には検証付きの一度限りのスクリプトを使う。スクリプトは整理後の取引 JSON と軌跡 JSON を事前に検証し、SQLite のバックアップを同じ `backend/data/` 内に別名で作成する。DB 内のサンプル行が保存用旧 JSON の16件と一致することを確認する。既に新 JSON と一致する状態での再実行は安全に完了し、それ以外の予期しないサンプル行や編集済みの旧サンプル行があれば更新を止める。

DB 更新は1つのトランザクションで行う。旧サンプル行とその品目を削除し、新しい37件と品目を挿入し、軌跡テーブルを整理後の12日分と完全一致させる。`meta` の初期化状態とサンプル以外の取引は維持する。検証・書き込み・同期の失敗時にはロールバックして旧 DB の内容を保つ。既存の backend 起動時の JSON→軌跡テーブル同期は維持し、以後の起動でも同じ12日分になる。取引を毎起動時に上書きする仕組みは追加しない。バックアップと更新後の DB ファイルは Git の追跡対象にしない。

## 検証

- 取引 JSON が37件で、定義した重複キーが一意であり、ID、日付、品目合計が正しいことを確認する。
- 軌跡 JSON が12日分で、全イベント・区間・経由地点の参照が存在し、取引 ID と日付が一致することを確認する。残った交通区間の根拠と、根拠がなくなった区間の推定表示を確認する。
- Vite mock API が整理後の JSON を初期データとして返し、追加・削除の操作を従来どおり行えることを確認する。軌跡の日付選択と地図・時系列の対応を確認する。
- 置換処理を一時 DB でテストし、旧16件から新37件への置換、利用者取引の保存、再実行時の安全性、不一致・書き込み失敗時のロールバックを確認する。
- 実 DB に適用した後、取引37件、軌跡12日、旧サンプルの不要行なし、バックアップありを読み取りで確認する。backend の取引 API と軌跡 GET、frontend のビルドとテストを実行する。
- 概要ページはデスクトップ幅と電話幅で、ナビゲーション直後の最初の表示に選択月と収支または記録アクションが見えることを確認する。プレビューが使えない場合は描画構造を確認し、その制限を報告する。
