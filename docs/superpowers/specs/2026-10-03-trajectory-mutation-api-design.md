# 軌跡データの新規・編集・削除 API 設計

## 目的と範囲

ローカルの Kakei API に、軌跡の「日」「訪問イベント」「移動区間」「地点情報」を新規・編集・削除する API を追加する。変更用エンドポイントは厳密に `POST`・`PUT`・`DELETE /api/trajectory` の3本とする。既存の `GET /api/trajectory/{date}` は保存済みの結果を返し、API による変更はサーバー再起動後も残る。今回変更するのは FastAPI、SQLite、API 文書とテストであり、React の軌跡画面と Vite の mock API は対象外とする。

軌跡画面は現在、固定 JSON を直接読む。したがって今回の API 更新は同画面へ反映されない。既存の取得 API のレスポンス形状は `{ "places": { ... }, "days": [{ "date": "...", "events": [...], "legs": [...] }] }` のままとする。

## 現状と選択した方法

現在の SQLite には地点、日、イベント、区間、経由地点のテーブルがある。起動時には `front/src/data/september-timeline.json` を検証し、全軌跡行を置換している。このままでは API による編集が再起動時に消える。

SQLite を軌跡の正本とし、固定 JSON は初回だけ投入する。個別の登録・削除を可能にするため、保存中の1日は未完成でもよい。たとえばイベント0件の日、隣り合うイベント間の区間がまだ登録されていない日を許す。完成した日だけを保存する方式では、区間単体の削除や、地点から順に組み立てる操作が成立しないため採用しない。

## API 契約

| メソッド | パス | 成功時 | 操作 |
| --- | --- | --- | --- |
| `POST` | `/api/trajectory` | `201` | 指定した種類の要素を作成 |
| `PUT` | `/api/trajectory` | `200` | 指定した要素の内容を全体置換 |
| `DELETE` | `/api/trajectory` | `204`、本文なし | 指定した要素を削除 |

3本は共通の JSON 本文を使う。`kind` は `day`、`event`、`leg`、`place` のいずれかとする。`POST` と `PUT` は `data` が必須で、`DELETE` は `data` を受け付けない。`date`、`id`、`fromEventId`、`toEventId` は要素の識別子であり、`PUT` では変更できない。識別子を変える場合は削除と作成を行う。未知のキーは `400 validation_error` とする。

| `kind` | 識別子 | `data` の内容 |
| --- | --- | --- |
| `day` | `date` | `events` 配列と `legs` 配列。空配列を許す。各イベントは既存 GET と同じ `id`、`time`、`placeId`、任意の `transactionId` を持つ。各区間は `fromEventId`、`toEventId` と任意の区間属性を持つ |
| `event` | `date`、`id` | `time`、`placeId`、任意の `transactionId` |
| `leg` | `date`、`fromEventId`、`toEventId` | 任意の `modeHint`、`transportTransactionId`、`viaPlaceIds`。空オブジェクトは移動手段を推定しない区間を表す |
| `place` | `id` | `name`、`address`、`coordinates`、`sourceUrl` |

例として、地点を登録した後、空の日とイベントを順に登録できる。

```http
POST /api/trajectory
Content-Type: application/json

{"kind":"day","date":"2026-10-03","data":{"events":[],"legs":[]}}
```

```http
POST /api/trajectory
Content-Type: application/json

{"kind":"event","date":"2026-10-03","id":"visit-1","data":{"time":"09:00","placeId":"shibuyaStarbucks"}}
```

`POST` と `PUT` は、識別子と保存後の正規の `data` を含む同じ形式の JSON を返す。`day` の `events` は時刻順、`legs` は始点イベントの順とする。`DELETE` は識別子だけを受け取る。本文上限は3本とも 1 MiB とする。既存の同一 Host・Origin 制限と `Cache-Control: no-store` を適用し、取引 DB の初期化は要求しない。取引 ID は従来と同様、取引テーブルへの外部キーにはしない。

## 保存規則と個別操作

- `day` の作成・編集は `events` と `legs` を1回の操作で保存する。編集ではその日のイベントと区間を全体置換する。日付は変えない。他の日と地点は維持する。日全体の削除では、その日のイベントと区間も削除し、共有地点は残す。
- `place` の ID と `event` の ID は呼び出し側が指定する。イベント ID は全日で一意とする。地点を編集すると、その地点を参照する全日に結果が反映される。イベントまたは区間の経由地点から参照される地点は削除できない。
- イベントは日の中で時刻順に並べる。時刻は同じ日で重複できない。イベントの追加・時刻編集で既存の区間が隣接イベント間を結ばなくなる場合は `409 conflict` とし、日全体の `PUT` でイベントと区間をまとめて組み替えられるようにする。区間から参照されるイベントの個別削除も `409 conflict` とする。
- 区間は、既存かつ隣接する2イベント間にのみ作成でき、同じ隣接ペアには1件までとする。区間の編集は移動手段・交通取引 ID・経由地点の内容を全体置換する。始点と終点の変更には削除と作成を使う。区間を削除しても両端のイベントは残る。
- 未完成の日の GET は、保存済みイベントと区間だけを既存形式で返す。`places` には、その日のイベント・経由地点が参照する地点だけを含める。未使用の地点を列挙する GET は今回追加しない。

## 検証とエラー

固定 JSON の初期投入では既存の `validate_timeline` を使い、各日にイベント2件以上、隣接ペアごとに区間1件というサンプルの厳格な条件を維持する。API 更新では、この完全性条件だけを緩める。実在する `YYYY-MM-DD`、`HH:mm`、空でない ID と名称、HTTPS の出典 URL、有限の東京範囲内の座標、既知の `modeHint`、鉄道・バス区間の `transportTransactionId`、地点参照、時刻順、区間の隣接関係を検証する。イベントと区間の取引 ID は空でない文字列かだけを確認し、取引テーブル内での存在は要求しない。

`400 validation_error` は本文の形・値・参照先の不正、`404 not_found` は編集・削除対象または指定日が存在しない場合、`409 conflict` は ID 重複、参照中の削除、既存区間とイベント順序の衝突に使う。JSON 形式や Content-Type、容量超過、Origin、DB 障害には既存 API の共通エラー規則を使う。失敗時は変更を一切保存しない。

## 初期投入と既存コマンド

サーバー生成時、`meta` に軌跡初期投入済みの印がない場合だけ固定 JSON を読む。軌跡テーブルが空なら検証後に1回だけ投入し、印を保存する。既存 DB に軌跡行がある場合はその行を維持して印を保存する。印があれば JSON の更新内容を自動同期しない。全日を API で削除しても印を消さず、再起動でサンプルが復活しないようにする。

API での初回変更時に軌跡編集済みの印を保存する。既存のサンプル置換コマンドは軌跡も全件置換するため、この印がある DB では明示的なエラーで停止し、取引も軌跡も変更しない。編集前の DB では従来の置換を続け、初期投入済みの印を保存する。API 文書と README から「起動ごとの完全同期」の説明を除き、この初回投入規則に更新する。

## 実装の境界

`api/trajectory.py` は3つの HTTP 操作、本文読取、エラーへの変換を担当する。`services/trajectory_validation.py` は初期 JSON の検証を維持し、API 更新用に未完成の日を扱える検証を追加する。`db/trajectory_store.py` は要素の読取・書込を担い、`db/store.py` は `BEGIN IMMEDIATE` の1トランザクション内で存在・参照・一意性を確かめて変更を確定する。`api/app.py` は初回投入と軌跡操作の未初期化例外を扱う。必要なスキーマ変更は `db/schema.py` に追加する。

既存テーブルの `position` は、イベントでは時刻順の番号、区間では始点イベントの番号とする。区間が欠けても番号を詰めず、GET はこの順に返す。イベントの挿入・編集で番号が変わる場合は、同じトランザクションで影響する区間の番号も更新する。

## 検証計画

- 4種類の要素について `POST`・`PUT`・`DELETE` と GET による保存結果を確認する。日全体の一括作成・置換、空の日、区間の欠けた日を含める。
- 重複 ID、存在しない地点・イベント、非隣接区間、参照中の削除、並べ替えで区間が不正になる場合、日付・時刻・座標・交通条件の誤りを確認する。
- 失敗した複数行更新がロールバックされること、取引未初期化でも操作できること、Host・Origin 制限、本文上限を確認する。
- アプリを同じ DB で作り直し、編集済みの日と、全日削除後の空状態が保たれることを確認する。固定 JSON の初回投入、既存軌跡行の移行、編集後のサンプル置換拒否を確認する。
- 現行12日分の `GET /api/trajectory/{date}` が初回投入直後に従来と同じ結果を返すことを確認する。画面は変更しないため、画面テストや画面の視覚確認は今回の完了条件に含めない。
