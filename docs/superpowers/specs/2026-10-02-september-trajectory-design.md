# 2026年9月の生活軌跡デモ — 設計

## 目的と確認できる状態

軌跡ページで、東京で暮らす架空の人物の2026年9月1日から30日までの取引を日付ごとに見られるようにする。交通に関する品目、店名、取引時刻を結び、当日の訪問地点を時刻順に並べ、地図上に推定移動経路を描く。利用者は日付を切り替え、地図と時系列一覧の対応を確認できる。

これは位置履歴ではない。実在する駅・店舗の名称と所在地を参照する一方、購入、時刻、金額、訪問順、移動は架空のサンプルである。画面上で「サンプル」「推定経路」を明示し、実際に通った道や乗った列車を断定しない。

## 対象と既存データ

- `#trajectory` は既存のアプリ内ナビゲーションにある空の画面を置き換える。公開マーケティング画面は変更しない。
- 旧サンプル16件は独立した `old-samples.json` に、現行の2026年9月分の値を保持する。旧 JSON は新 JSON へ書き換えない。
- 新しい `trajectory-samples.json` に2026年9月の取引、地点、時刻、経由地点を独立して保存する。
- 新規に初期化するアプリでは、新 JSON の**取引部分**を概要ページの初期サンプルとして登録する。既存のローカル DB に保存済みの旧サンプルや利用者の取引は変更、削除、移行しない。
- 軌跡ページは常に新 JSON のデモを表示する。既存 DB の概要ページと内容が異なる場合にも、その区別が分かる「2026年9月の軌跡サンプル」という表示を付ける。サンプル削除や通常取引の追加は、この固定デモを変更しない。
- 通常取引の入力、API、DB スキーマに時刻や位置のフィールドは追加しない。

## サンプルデータ

新 JSON は9月の30日すべてに、少なくとも2つの訪問地点とその日に発生した取引を含む。各取引は既存の `id`、`date`、`title`、`type`、`category`、`amount`、`merchant`、`paymentMethod`、`items` 形式に適合する。支出の品目金額の合計は取引金額に一致させる。交通費は「電車」「バス」などの一般名だけでなく、乗車区間を読める品目名を使う。

同じ JSON 内の軌跡専用データは取引 ID を参照し、時刻、地点 ID、移動手段を示す根拠、必要な経由駅または経由地点を持つ。地点カタログは名称、住所、経度・緯度、所在地を確認した出典 URL を持つ。所在地と店舗の実在性は駅や店舗の公式情報で確認する。購入したという事実や時刻・金額は実在情報として扱わない。架空の自宅住所は置かず、利用者の居住地を推定しない。

日別データは取引 ID との結合後に時刻順へ並べる。交通品目から区間の移動手段が分かる場合はその根拠を使う。交通の根拠がない地点間は「移動推定」として区別する。家賃、定期券購入、オンライン決済など、支払いから訪問を推定できない取引は地点に変換しない。線は確認済みの地点と指定された経由地点を結ぶ参考形状とし、道路や線路への正確な追従を主張しない。

JSON の検証条件は、9月の30日が揃うこと、日別イベントが時刻順であること、参照する取引・地点が存在すること、座標が東京内にあること、各日の地点と区間が描画できること、品目合計が合うこと、重複 ID がないこととする。

## 画面構成と操作

画面先頭に「2026年9月の軌跡サンプル」、選択日、前日・翌日ボタン、30日から選べる日付選択を置く。続いて立ち寄り件数、当日の支出額、移動手段、概算距離を短く表示する。距離は経路頂点に沿う参考値として「概算」を付ける。

デスクトップでは地図と時系列一覧を横に並べる。電話幅では日付と概要の次に地図、その下に一覧を置く。地図には訪問順の番号付き地点と経路を描き、徒歩、交通機関、移動推定を線種と文字の凡例で区別する。地点または一覧項目の選択は双方の強調状態を同期し、一覧には時刻、店名・駅名、交通品目または購入品目、金額を表示する。取引のない通過駅は取引と混同しない名称で示す。

日付変更ではその日の地点を収める範囲へ地図を合わせる。アニメーションを減らす設定を尊重する。操作にはキーボードで使えるボタンと選択欄を使い、地図上の選択に依存せず一覧から同じ情報を読めるようにする。地図の読み込み中、トークン未設定、WebGL 非対応、地図通信エラーでは地図領域に状態と対処を表示し、日付選択と時系列一覧は維持する。空の日付はこの固定デモには存在しない。

視覚は `DESIGN.md` の白い背景、Ink の文字、Cloud Card の面、丸み、余白、抑えた指標色に従う。`MASTER.md` は残りの一般 UX に適用し、公開ページ用のパターンは使わない。`ui-ux-pro-max` のアクセシビリティ、操作、地図の代替一覧に関するガイドを適用する。電話幅で横スクロールを生じさせず、操作対象は少なくとも44pxを確保する。

## 構成と技術

1. JSON を読み込む独立したデータ層が取引と軌跡情報を検証・結合し、選択日について時系列イベント、訪問地点、区間、支出合計を返す。地図コンポーネントは取引の意味付けを行わない。
2. Mapbox GL JS はベース地図とカメラ、パン・ズームを担当する。公開アクセストークンは Vite の環境変数から受け取り、リポジトリには埋め込まない。
3. deck.gl の `MapboxOverlay` に `PathLayer`、地点用レイヤー、番号用レイヤーを載せる。選択日と選択地点が変わったときにレイヤーを更新し、画面を離れると地図と overlay を破棄する。
4. Turf.js は区間の距離と地点・線の表示範囲を計算する。地理計算の結果は「概算」とし、正確な実走距離と表現しない。
5. 軌跡画面と地図を別コンポーネントに分け、地図の通信・WebGL 状態から一覧を独立させる。地図関連ライブラリは軌跡画面でのみ読み込む。

Mapbox Directions API による毎回の経路探索や任意の店名の自動ジオコーディングは対象外とする。東京の固定サンプルに対して検証済み地点と参考経由点を JSON に保存し、再現性を優先する。

## 検証

- データ層のテストで30日分、品目合計、時刻順、地点参照、交通区間の対応、旧・新 JSON の独立性を確認する。
- 新規初期化では新 JSON の取引が概要ページへ入り、既存 DB を読み込む場合は保存済み取引を変更しないことを確認する。
- 画面テストで日付移動、時系列と地点の同期、地図失敗時の一覧、キーボード操作を確認する。
- デスクトップと375pxの電話幅で、先頭に選択日と概要が見えること、地図と一覧の順序、横スクロールがないことを確認する。トークンが利用できる環境では地図と経路を視覚確認し、利用できない場合はその制限を報告する。
